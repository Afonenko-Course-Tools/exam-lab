# Подготовка существующей Windows

`setup/Prepare-ExamLab.ps1` — отдельный инструмент для уже установленной Windows.
Он проверяет и устанавливает IDEA, JDK, Git и Gradle. QEMU, WinRM, специальные учётные
записи и ISO для него не нужны. Скрипты `scripts/vm/` обслуживают только
испытательную VM и не являются способом развёртывания в аудитории.

## Поддерживаемые предпосылки и границы испытаний

Общий нижний предел выбранных x64 установщиков — клиентская Windows 10
1809, build 17763. Для установки и проверки работы нужен PowerShell 7.6 x64.
Предварительное обследование работает в Windows PowerShell 5.1 x64. Ранее выпущенные
Windows, x86, ARM64 и Windows Server скрипт не подготавливает автоматически.
Windows 11 и разные редакции проверяются по возможностям, но наличие подходящей
версии ОС не означает, что на ней пройден экзаменационный пилот.

Основания: [требования IDEA именно версии 2025.2](https://www.jetbrains.com/help/idea/2025.2/installation-guide.html),
[требования Git for Windows](https://gitforwindows.org/requirements.html),
[параметры Windows MSI Temurin](https://adoptium.net/installation/windows).
IDEA содержит собственный JBR 21; отдельный JDK 25 нужен для учебных проектов.
Минимум IDEA — 2 GiB свободной памяти и 3,5 GB диска; рекомендуется 8 GiB общей
памяти и SSD с 5 GB свободного места. Для загрузки и временной копии установщиков
нужно дополнительное место. Скрипт сообщает свободную память; это не замена
проверки производительности на конкретном ПК.

Готовность Shared PC определяется отдельно: [Microsoft указывает](https://learn.microsoft.com/en-us/windows/client-management/mdm/sharedpc-csp)
Pro, Enterprise, Education и IoT Enterprise начиная с Windows 10 1607.
Home не проходит обычный `Prepare`: экзаменационный Guest на этой редакции
не поддерживается. Подготовка одних программ допускается только явным
`-SoftwareOnly`; `SharedPCPlatformEligible` остаётся отрицательным. Наличие класса MDM bridge проверяется чтением при
запуске администратора. Подготовка его не включает и не меняет политики.
Домен, MDM и ранее заданные ограничения требуют отдельного испытания.

Фактически исходный эталон установлен на Windows 10 Enterprise Evaluation
22H2 `19045.2006`. Общий скрипт отдельно испытан на изменяемой копии этого эталона;
конкретные результаты приведены ниже.
Другая сборка или редакция не объявляется проверенной по одному сравнению версий.

## Самая ранняя проверка Windows

До инвентаризации, загрузки, создания временного каталога и установки
проверяются контекст запуска, native x64 и редакция/build. Целевая архитектура —
native x64 (AMD64). Она определяется
по `pNativeMachine=AMD64` (`0x8664`)
из [IsWow64Process2](https://learn.microsoft.com/en-us/windows/win32/api/wow64apiset/nf-wow64apiset-iswow64process2):
архитектура эмулируемого процесса не считается архитектурой ОС.
[GetNativeSystemInfo при эмуляции может возвращать сведения об эмулируемом процессоре](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation).
API доступен с Windows 10 1709; сборки ниже общего минимума 17763
отклоняются до его вызова с диагностикой конфликта.
Результат `Preflight` отдельно содержит известные минимумы и
фактическую доступность:

- SharedPC: семейство редакции, build не ниже 14393, наличие MDM bridge класса;
- локальная MLGPO: штатные gpedit.dll/gpupdate.exe и регистрация GroupPolicyObject;
- NetSecurity, ScheduledTasks и LocalAccounts: штатный путь и версия модуля.
  При `Prepare` и `Verify` также проверяются необходимые команды и
  административный запрос на чтение;
- службы Schedule, BFE, MpsSvc, gpsvc: наличие, текущий статус и отсутствие Disabled.

Для MLGPO [IGroupPolicyObject2 существует с Windows Vista](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/policy/igrouppolicyobject2),
но общий software floor здесь Windows10 1809. Регистрация COM сверяется по
[CLSID из Microsoft gpedit.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/GPEdit.h).
Проверка файлов/регистрации не заменяет реальную запись и действие MLGPO:
при подготовке политики не применяются. Штатный demand/trigger-start service
может быть остановлен; это отличается от отключённой или отсутствующей службы.
Недоступное наблюдение сообщается как UnknownOrUnavailable, не как доказанное
отсутствие возможности.

Обычный Prepare блокируется, если экзаменационные предпосылки не подтверждены.
Явный `-SoftwareOnly` разрешает подготовку IDEA, JDK, Git и Gradle при соблюдении их
предела ОС; это не разрешает включить политики на неподдерживаемой редакции.
Проверка версии не означает испытание поведения. `MatchesTestedOsBuild`
обозначает совпадение ОС со стендом, а не приёмку текущего ПК.

## Команды

`Check` можно запустить до повышения и установки PowerShell 7. Для `Prepare`
и `Verify` нужен повышенный административный запуск в PowerShell 7.6 x64.
Используйте проверенную локальную копию исходников.
В примерах `-ExecutionPolicy Bypass` разрешает её запуск при стандартной клиентской
политике `Restricted` только в новом процессе PowerShell и его дочерних процессах;
сохранённые политики `LocalMachine` и `CurrentUser` не меняются.
Доменная Group Policy (`MachinePolicy`/`UserPolicy`) имеет приоритет над этим
параметром; он не отменяет её запрет запуска. См.
[политики выполнения PowerShell 7](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-7.6).

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\setup\Prepare-ExamLab.ps1 -Action Check -ReportPath .\check.json
```

`Check` читает реестр, метаданные программ, известные каталоги и пути команд.
Поля `Plan.Actions`, `Plan.Packages` и `Plan.Blockers` перечисляют действия,
необходимые установщики и причины блокировки. Работа инструментов и
административное чтение модулей на этом этапе остаются непроверенными.
При указанном `ReportPath` записывается только выбранный отчёт. Обследование
видит установки HKLM и текущего пользователя. Обход чужих профилей и всех дисков
в поиск не входит.

`Verify` подтверждает версии с `java --version`, `javac --version` и
`git --version`. В защищённом временном каталоге Program Files он компилирует
и запускает небольшой Java-класс и выполняет Git `init/status`, затем удаляет
каталог. Дочерние процессы запускаются с очищенными переменными внедрения Java и Git.
Git использует пустой template и отключает конфигурацию из профиля и системы.
Проба запускает программы из путей, защищённых от записи обычным пользователем.
Такую же проверку выполняет `Prepare` после установки.

Для Gradle `Check` определяет версию по имени `gradle-core` и проверяет наличие
`bin\gradle.bat`, соответствующего `gradle-launcher` и каталога `lib\plugins`.
Для выбранного каталога и его содержимого проверяются владельцы, ACL и отсутствие
точек повторной обработки. Gradle и учебную сборку запускают из учётной записи
ученика с выбранным JDK 25.

В окне PowerShell от администратора:

```powershell
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\setup\Prepare-ExamLab.ps1 -Action Prepare -ExpectedPlanPath .\check.json -ReportPath .\prepare.json
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\setup\Prepare-ExamLab.ps1 -Action Verify -ReportPath .\verify.json
```

`-ExpectedPlanPath` необязателен. С ним `Prepare` до запуска установщиков
сверяет действия, выбранные версии и пути с сохранённым отчётом `Check`.
При расхождении выполните `Check` повторно и проверьте новый план.

Скрипт устанавливает IDEA Community `2025.2.6.4`, Temurin JDK `25.0.5+8`,
Git for Windows `2.56.1` и Gradle `9.8.2`. Ссылки и SHA256 указаны в константах
скрипта и документации. [IDEA, JDK и Git](windows-vm.md#источники),
[дистрибутив и SHA256 Gradle](https://github.com/gradle/gradle-distributions/releases/tag/v9.8.2).

До первого установщика выполняются все проверки ОС, привилегий и конфликтов,
затем загружаются и проверяются все отсутствующие пакеты. Для каждого нужен
точный SHA256. Установщики IDEA, JDK и Git также требуют действительную
Authenticode-подпись ожидаемого издателя. ZIP Gradle проверяется по закреплённому
официальному SHA256, в отчёте это `ArchiveVerified`.
Файл из общего cache копируется из открытого потока в новый закрытый каталог
`Program Files\ExamLab-Setup-<случайное имя>`, снова проверяется и используется
оттуда. Поток открыт без разрешения записи и удаления до завершения установки.
ACL существующего cache не меняется. Журналы и резервная копия плагина остаются
в закрытом временном каталоге, указанном в `WorkingDirectory` отчёта.

Для автономной установки заранее скопируйте файлы нужных программ с именами
из констант скрипта в отдельный каталог. Для Gradle используйте `gradle-9.8.2-bin.zip`.

```powershell
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\setup\Prepare-ExamLab.ps1 -Action Prepare -CacheDirectory D:\ExamLabInstallers -ReportPath .\prepare.json
```

Существующий cache с неправильным хешем не заменяется молча. При отсутствующем
файле нужен доступ к официальному URL; загрузка идёт сразу в закрытый staging,
общий cache скрипт не создаёт и не изменяет. Цепочка подписи должна проверяться
Windows для установщиков IDEA, JDK и Git.

Корень Gradle создаётся внутри закрытого промежуточного каталога с собственным ACL.
SYSTEM и Administrators получают полный доступ, Users и Guests — чтение и запуск.
Права `Program Files` на корень дистрибутива не наследуются. После проверки
структуры и прав целый каталог переносится в `%ProgramFiles%\gradle-9.8.2`.

## Существующие программы и безопасный повтор

Подходящими считаются Community IDEA `2025.2.x`, полноценный JDK `25.x`
с работающим `javac`, Git не ниже `2.56.1` и Gradle `9.8.x` начиная с `9.8.2`.
Скрипт сохраняет самую свежую из найденных подходящих установок Gradle.
Они ищутся в каталогах `gradle-*` в `Program Files` и `Program Files\Gradle`,
через `GRADLE_HOME` и по `gradle.bat` в `PATH`. [Выпуски Gradle](https://gradle.org/releases/).
Для IDEA проверяются `productCode=IC`, версия и наличие `idea64.exe`; CLI
проверки не подтверждают работу графической IDE.

Если найдены только неподходящие IDEA, Git или Gradle, выберите имеющуюся
подходящую установку явно.

```powershell
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\setup\Prepare-ExamLab.ps1 -Action Check -IdeaPath 'C:\Tools\IDEA-2025.2' -JdkPath 'C:\Tools\jdk-25' -GitPath 'C:\Tools\Git' -GradlePath 'C:\Gradle\gradle-9.8.2'
```

Для автоматически найденных IDEA и Gradle флаг `-InstallAlongside` разрешает
параллельную установку в свободный каталог. Несовместимый существующий Git
требует отдельного решения администратора.

Из путей JDK, заканчивающихся на `bin`, скрипт получает корень JDK. Когда
пригодного JDK 25 нет, Temurin устанавливается в `%ProgramFiles%\ExamLab-JDK-25`.
Установщик включает только `FeatureMain`. Непригодный зарегистрированный Temurin 25
блокирует установку MSI, поскольку новая сборка той же основной версии способна
изменить существующий Temurin. Явный неподходящий `-JdkPath` также блокирует установку.
ExamLab - IDEA задаёт выбранный `JAVA_HOME` только своему процессу и передаёт
свойства Gradle в отдельном каталоге ExamLab в профиле. У обычных запусков остаются
прежние `JAVA_HOME`, `PATH` и каталоги настроек.

Для замены конкретной IDEA укажите `-ReplaceIdeaPath` с её полным корневым путём
при `Check` и `Prepare`. Скрипт проверяет версию, однозначную машинную запись и
штатный `bin\uninstall.exe`. После проверки подписи и хеша нового установщика
скрипт вызывает деинсталлятор и ставит версию из комплекта. Такой порядок сохраняет
однозначность записи Windows при замене сборок, использующих один ключ удаления.
При работающем целевом экземпляре или его пути в `PATH` замена
блокируется. Тем же параметром обычный повтор подтверждает уже установленную версию.
Деинсталлятор JetBrains в тихом режиме сохраняет стандартные настройки и кэш.
[Сценарий JetBrains](https://github.com/JetBrains/intellij-community/blob/master/build/conf/nsis/idea.nsi) ·
[Параметры удаления JetBrains](https://github.com/JetBrains/intellij-community/blob/master/build/conf/nsis/DeleteSettings.ini)

Установщики запускаются без автоматической перезагрузки. Код MSI `3010`
сохраняется как `RebootRequired=true` и итоговый код `3010`. При частичном отказе
успевшие установки не откатываются; повтор обнаруживает их и продолжает с
отсутствующими программами. Отчёт содержит фактические версии и коды установщиков.
Скрипт сверяет сохранность `JAVA_HOME`, `GRADLE_HOME` и `PATH`. Temurin получает
только `FeatureMain`, Git — `PathOption=BashOnly`, IDEA — `updatePATH=0`.
Для учебного проекта с локальным Gradle в IDEA укажите `After.Gradle.Selected.Path`
в качестве дистрибутива и `After.JDK.Selected.Path` в качестве Gradle JVM.
Для пробы в обычном PowerShell задайте `JAVA_HOME` только для текущего процесса
и вызовите `bin\gradle.bat` по абсолютному пути с параметром `--version`.
Сохранность существующих занятий подтверждается отдельным входом и запуском
обычного проекта.

## Генеративные дополнения и ручные проверки

Из новой установки IDEA скрипт перемещает поставляемый каталог `fullLine`
и файл `plugins/plugin-classpath.txt`, если они есть, в новую закрытую резервную
копию до запуска IDE. Full Line Code Completion — локальный генеративный плагин.
Файл `plugin-classpath.txt` содержит заранее подготовленные описания bundled
плагинов: один перенос каталога оставляет описание Full Line активным и вызывает
ошибки загрузки его классов. Без этого файла IDEA штатно сканирует оставшиеся
каталоги плагинов. Собственный разбор или переписывание файла не используется.
Этот механизм подтверждён по поставке IDEA Community 2025.2.6.4; совместимость
другой установки в inventory не заменяет проверку её запуска после исключения.

В существующей IDEA такое изменение делается только с явным
`-DisableBundledGenerativePlugins`, после закрытия IDEA и проверки защищённости
путей. Повтор исправляет и случай, когда `fullLine` уже перенесён, но
`plugin-classpath.txt` остался. Прежние резервные копии не перезаписываются.
Описание переносится первым. При частичном отказе скрипт возвращает ошибку,
сохраняет уже перенесённые файлы и их пути в отчёте; автоматического отката нет.
После устранения причины повтор обрабатывает оставшиеся файлы.
Остальные плагины не удаляются и профили пользователей не переписываются.
Отчёт Check перечисляет известные каталоги и наличие `plugin-classpath.txt`;
он не подтверждает отсутствие генеративных помощников или чистый запуск IDEA.
Пользовательские и иные плагины требуется проверить в GUI. Работу SDK,
индексации и запуска проекта проверяют отдельно: устранение сохранённого
описания Full Line само по себе не доказывает исправление этих функций.

`SoftwareReady`, `SharedPCPlatformEligible`, `CLIProbe` и ручные проверки —
разные результаты. `SoftwareReady` учитывает структуру и права Gradle, а также
CLI-пробы Java и Git. `ExamReady` остаётся `false`: подготовка инструментов не
подменяет испытание настоящего Guest, IDEA SDK/run/debug, обычного дополнения
кода, инспекций и рефакторинга, Moodle/PrairieLearn, физических USB, завершения
без сервера и сохранности обычных занятий.

Код `0` означает выполнимый план для `Check` и готовность программ для
`Prepare` и `Verify`. Код `2` сообщает о конфликте или неподтверждённой
готовности, `1` — об ошибке, `3010` — о необходимости перезапуска Windows.
Рекомендуется сохранить JSON целиком: в нём нет паролей и ключей продуктов,
но присутствуют локальные пути и состояние рабочей станции.

## Результат проверки общего скрипта

15 ноября 2026 года на отдельной копии Windows 10 Enterprise Evaluation 22H2
`19045.2006`, en-US, Windows PowerShell 5.1 выполнены проверки версии скрипта с
IDEA, JDK и Git, выпущенной до добавления Gradle:

- Check исходных установок с компиляцией/запуском Java и Git init/status;
- установка всех трёх отсутствующих программ: три подписи/хеша до первого
  установщика, все exit codes 0, затем фактические версии и CLI smoke;
- повтор Prepare без cache: только PreservedCompatible, без установщиков;
- неподходящий явный GitPath: отказ exit2 до изменений;
- существующий настоящий Temurin21.0.13+9: отказ без флага и установка25 рядом
  с `-InstallAlongside`, с сохранением JAVA_HOME/PATH на21;
- обычный labstudent с nonadmin token компилировал и запускал прежний учебный
  проект через default21 до и после. SHA256 JDK21/release и обоих исходных
  учебных файлов совпали; абсолютный25 отдельно прошёл CLI smoke;
- полный fresh-install прогон с реальными кириллицей и пробелами в пути
  самого скрипта, CacheDirectory и ReportPath. IDEA использовала quoted
  CONFIG/LOG, Full Line исключён с резервной копией, среда сохранена.

Первоначальные диагностические прогоны выявили старое ожидаемое имя издателя
Git и неверные предположения о native GPO/LocalAccounts bindings. Исправленные
проверки выполнены на настоящей Windows; отказы до установки не считаются
успешными установками.

Расширение списка известных Pro/Enterprise вариантов SKU проверено отдельным
Check/повтором без переустановки. После замены проверки архитектуры на
`IsWow64Process2` выполнены штатный разбор скрипта Windows PowerShell 5.1
(0 ошибок) и отдельный `Check` на той же x64-копии из нового закрытого каталога:
`NativeMachine=0x8664`, `NativeX64=true`, код 0, `SoftwareReady=true`,
`ExamReady=false`, `Changes=[]`, `Errors=[]`, среда сохранена. Установки и
экзаменационные политики в этом прогоне не запускались. Эта проба подтверждает
положительный путь на целевой x64; отказ на неподдерживаемой архитектуре и
отказ старой ОС реально не испытаны.
Фактические установщики возвращали0: ветка3010 реализована, но на стенде
перезагрузку они не запрашивали. ARM64/x86, Windows11, другие редакции/сборки,
Server, domain/MDM и сама русская Windows не испытаны. Кириллические имена на
en-US подтверждают обработку путей, но не являются приёмкой ru-RU ОС.
WinRM используется только тестовой обвязкой стенда, не самим setup.

## Установка экспериментального локального пилота

`setup/Install-LocalPilot.ps1` доставляет переключатель на существующую standalone
Windows client build19041+ с native AMD64 и повышенным административным token.
QEMU, WinRM, определённый производитель и `ProgramData\ExamLab-TestVM` не требуются.
Нижний предел компонентов отличается от software floor 17763 общего Check/Prepare.
До доставки проверяются native x64 через `IsWow64Process2`, PowerShell 7 x64,
client/build и отсутствие домена. Исходники, подписи, конфигурация и ACL сохраняют
свои проверки. Это отдельный этап после проверки инструментов.

Установка не означает допуска экспериментальных политик к рабочим ПК: их применение
по-прежнему разрешено только на отдельной одноразовой VM. Прежняя native-приёмка
относилась к отмеченному QEMU-стенду; путь без маркера и остальные Windows ещё
требуют отдельного native-испытания.

```powershell
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\setup\Install-LocalPilot.ps1 -LGPOPath 'D:\LGPO_30\LGPO.exe' -ConfigurationPath 'D:\ExamLab\pc.json' -PolicyFileEditorPath 'D:\PolicyFileEditor-3.0.1'
```

LGPO3.0 берётся из официального [Security Compliance Toolkit](https://download.microsoft.com/download/8/5/c/85c25433-a1b0-4ffa-9429-7e023e7da8d8/LGPO.zip).
Скрипт проверяет фиксированный SHA256 и Valid Microsoft Authenticode. В
Program Files\ExamLab устанавливаются основной, USB и сетевой модули, входной PS1,
LGPO.exe, точный offline PolicyFileEditor 3.0.1 с LICENSE и четыре
фиксированных task-*.ps1 wrapper; у SYSTEM/Administrators полные права, у Users
только чтение/выполнение. ProgramData\ExamLab доступен только SYSTEM/Administrators.
Туда копируется явно переданный `pc.json`, например:

```json
{"OrdinaryAccounts":[{"Sid":"S-1-5-21-111111111-222222222-333333333-1001","Name":"labstudent"}]}
```

Замените пример на фактические SID и имена обычных локальных пользователей.
Пустой список, повторы и неизвестные параметры отклоняются; автоматического
выбора учётных записей нет. Необязательный `Network` описан в
[договоре локального модуля](local-pilot.md); USB новых config keys не требует.
Исходный offline пакет, адресное снятие USB source и действие Non-Administrators
на обычные учётные записи описаны в [USB-компоненте](windows-usb-policy.md). Если есть `mode.json`, SHA256 конфигурации должен
совпадать с его `Revision`: установщик не меняет roster молча и не перезаписывает
metadata режима. `Revision` обозначает только собственную конфигурацию, не снимок
настроек Windows. Повтор использует общий с действиями модуля exclusive lock.
Старый `state.json` всегда блокирует установку до копирования и изменения задач:
нужен отдельный разбор прежнего цикла с сохранением его кода и данных.
Исторические `baseline-*` каталоги сами по себе не активны и не удаляются.

На время доставки прежние фиксированные задачи отключаются и проверяется,
что они не выполняются; новые задачи сначала создаются Disabled. Только после
полной доставки и назначения SDDL они включаются. При частичном отказе
незавершённые задачи остаются Disabled; повтор восстанавливает установку.

Создаются только фиксированные административные задачи ExamLab-Local-prepare,
ExamLab-Local-check, ExamLab-Local-exam и ExamLab-Local-normal. Principal задаётся
SID S-1-5-18, ServiceAccount, Highest; task SDDL разрешает управление только
SYSTEM/Administrators, работа на батарее разрешена. Автоматических триггеров нет.
Прежние фиксированные задачи enable/finish отключаются и удаляются после проверки,
что они не выполняются. Установщик не запускает ни одно действие, не включает
политики, не меняет Shared PC и не вызывает общий Check/Prepare инструментов.
Действия `prepare/check/exam/normal` администратор запускает отдельно по
[договору локального модуля](local-pilot.md); журналы остаются приватными.

Ранее проверенная доставка четырёх фиксированных действий относилась к payload
до добавления USB, Network и offline PolicyFileEditor. Она не подтверждает новую
общую поставку компонентов; для неё нужна отдельная Windows-проверка.

Финальный Check общего setup также выполнен после узкого исправления catch:
ранний отказ до основной инвентаризации больше не запускает её из обработчика
ошибки. Негативный сценарий на другой неподдерживаемой ОС пока не испытан.
