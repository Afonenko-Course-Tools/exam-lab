## Предлагаемая точка сопоставления

1. Moodle открывает исходный подписанный LTI callback. Gateway заранее
   знает точную пару регистрации и элемента и разрешает опыт только для
   роли студента по явно включённому настройкой элементу. Подписанный
   callback сохраняет прежний сетевой допуск и выдаёт 303 на одноразовый
   **/gateway/courses/<course>/pl/<flow>**.
2. Отдельная тестовая поставка направляет этот 303 на тот же HTTPS hostname
   через второй выделенный порт. Базовый порт, Moodle URL и LTI registration
   сохраняют свои значения. **GatewayLogin** остаётся host-only, Secure,
   HttpOnly, SameSite=None, Path=/gateway. Один владелец доверия отвечает за
   оба порта, поскольку браузер отправляет эту cookie на подходящие пути
   обоих портов. [Область действия cookie](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)
3. Squid пропускает TLS без расшифрования только для точных authority,
   ожидаемого SNI и разрешённого адреса второго listener. Первичный
   CONNECT также проверяет Host, а повторная проверка на **SslBump2**
   разрешает только тот же ожидаемый endpoint. Существующее TLS bump
   правило для базового порта по-прежнему проверяет Moodle и PL.
   Nginx второго порта принимает только трафик от доверенного прокси,
   точные SNI и HTTP Host:port, а также ровно нужный маршрут handoff.
   Сервер просит клиентский сертификат отдельной экзаменационной CA.
   [Squid Peek and Splice](https://wiki.squid-cache.org/Features/SslPeekAndSplice) · [Настройки TLS Nginx](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_verify_client)
4. При **$ssl_client_verify = SUCCESS** Nginx передаёт идентификатор
   клиента только существующему внутреннему **auth_request** с его
   сервисной аутентификацией. Достаточна пара из фиксированного
   SHA-256 DER закреплённой CA и уникального TLS serial. Отдельный
   служебный секрет, доступный только выделенному Nginx и Gateway,
   подтверждает происхождение заголовка даже за прежним ingress.
   Значения из HTTP браузера очищаются. На втором порту нет публичного доступа к private handoff,
   Moodle, PL API или произвольному upstream. Для этой проверки отключают
   возобновление TLS и keep-alive на втором listener.
   [Проверка владения ключом в TLS](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.5.2)
5. Gateway сопоставляет клиентское подтверждение с уже проверенным LTI
   snapshot при атомарном употреблении обычного handoff. Nginx передаёт
   Native PL исходные заголовки подтверждённых UID/имени, **Host** базового
   origin и **X-Forwarded-Proto: https**. Адрес **Location** к bootstrap
   должен явно вернуть браузер на базовый порт. Для подтверждённого
   учебного входа достаточно передать необязательный идентификатор сертификата
   в существующем краткоживущем snapshot и сообщать о привязке после
   успешного **bridge.enroll**. Новая таблица попыток и изменение wire
   Bridge для этого не требуются.
   [Одноразовый Gateway handoff](https://github.com/Afonenko-Course-Tools/moodle-prairielearn-gateway/blob/2692e56b997e4c6856ae5b9e1def3844e3ef4568/src/gateway/store.py)
6. Контроллер передаёт панели имя и статус проверки для текущего кортежа.
   Для отсутствующего сертификата, неподтверждённого кортежа и ошибки
   записи имя не выводится. LTI без предъявленного сертификата проходит
   на отдельном порту при **ssl_verify_client optional**, LTI без
   включённого опыта использует базовый порт. Отклонённый предъявленный
   сертификат или недоступный дополнительный listener могут прервать
   именно включённый тестовый маршрут. Базовый маршрут служит вариантом
   возврата через отключение настройки до нового запуска Moodle.

Это штатное взаимное TLS на фактическом одноразовом переходе в PL. Доверие
распространяется на владение ключом в запросе handoff, текущий управляемый
Guest и проверенную учебную личность в том же переходе. Один сетевой адрес
по-прежнему допустим у нескольких зарегистрированных мест. Галочка проверки
готовности, вывод имени и отметка сдачи имеют самостоятельные основания.

## Выдача, срок и отзыв ключа

Подготовка Windows генерирует ключ в CNG под привилегированным ExamLab
из защищённого источника. Подходит стандартный запрос **certreq** с
**MachineKeySet = TRUE**, запрещённым экспортом и ACL на SYSTEM,
администраторов и право подписи для точного текущего Guest SID. Клиенту
выдают сертификат **Client Authentication** с отдельной тестовой CA.
Подпись связывает сертификат с защищённо созданным ключом. Профилю Edge
требуется ассоциация публичного сертификата с тем же машинным контейнером
ключа. Проверка этого шага на реальном Windows обязательна.
[Параметры certreq](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/certreq_1) · [Копирование контекста сертификата между хранилищами](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-certaddcertificatecontexttostore)

Учёт выдачи формируется из привилегированной регистрации текущего Windows
и свежего наблюдения WTS. Для временного опыта оператор сопоставляет
серийный номер с конкретным кортежем по этому каналу и выпускает только
публичный ответ на CSR. Рабочая выдача привязывает проверенный серийный
номер к тому же кортежу по существующему доверенному каналу устройства.
Сертификат действует в пределах назначенного опыта. Повторный выпуск и
перезапуск требуют нового ключа для нового Guest. Для защиты от устаревшего
сертификата сервер при каждой записи проверяет актуальность назначения и
полного кортежа под той же блокировкой контроллера, что и при опросе машины.

На следующем **present** для другого Guest, подтверждённом **absent**,
команде **normal**, изменении назначения, смене boot или отзыве
регистрации прежнее соответствие закрывается. При недостоверной связи
контроллер приостанавливает привязку до свежего наблюдения из того же
сеанса. История сохраняет имя завершённого гостя и время подтверждённого
выхода. Локальный **normal** удаляет собственную ассоциацию сертификата и
отзывает право старого SID на ключ без сервера. Очистка после перезагрузки
находит собственные оставшиеся объекты по защищённому учёту. Windows
проверяет право текущего Guest на подпись, отсутствие экспорта закрытого
ключа и отказ доступа к ключу прежнего сеанса.

Для автоматического выбора Edge задаётся **AutoSelectCertificateForUrls**
только для точного HTTPS host:port второго listener, с фильтром выделенной
CA. В профиле текущего Guest должен подходить ровно один сертификат.
Приёмка проверяет **edge://policy**, реальный запрос без выбора в диалоге,
обычный вход, следующий Guest и отказ старому ключу. Наличие политики в
документации указывает на доступный штатный механизм. Оно не подтверждает
поддержку конкретной сборкой и профилем стенда.
[Политика Edge](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/autoselectcertificateforurls) · [Точный порт в шаблоне URL](https://learn.microsoft.com/en-us/deployedge/edge-learnmore-ent-policy-url-patterns)

## Что записывает панель

- Внутренний **POST /exam/internal/lti-binding** принимает ровно поля
  **examId**, **certId**, **uid**, **student** в JSON. Секрет передачи
  задаётся отдельно через **Authorization: Bearer** и файл с 64 строчными
  шестнадцатеричными символами. **examId** берётся из серверного **examAudit**
  выбранного подписанного activity. **certId** состоит из SHA-256 DER
  закреплённой CA в нижнем регистре и TLS serial в верхнем регистре,
  разделённых двоеточием. UID имеет прежний формат Gateway. Имя
  отображается после принятия контроллером и содержит до 256 символов.
  Ответ **204** подтверждает запись или идемпотентный повтор. Отказ
  наблюдения оставляет подписанный учебный переход доступным.
- Только внутренний **auth_request** выделенного listener может
  передать пару **X-Exam-Client-Cert-Id** и **X-Exam-Client-Cert-Proof**.
  Gateway проверяет частный handoff, единственность обоих заголовков и
  отдельный закрытый **examBinding.proofTokenFile**. Закрытая подготовка
  контроллера связывает сертификат с назначением, зарегистрированным
  местом, ревизией, boot и конкретным Guest. Перед записью этот кортеж
  сверяется с его живым наблюдением. [Контроллер](../controller/server.py)
- Контроллер ищет единственный актуальный кортеж и хранит привязку по
  устойчивому UID. Один и тот же повтор UID для того же кортежа
  идемпотентен. Иной UID в одном сеансе или один UID на двух активных
  местах дают явный конфликт. Панель показывает причину преждевременной
  или неоднозначной привязки и историю только из подтверждённых наблюдений.
- Для дальнейшей интеграции основная строка использует **sessionStudent**
  и отдельный статус источника, например «подтверждено LTI», «ожидание»
  или «конфликт». Текущее поле **student** описывает ручную рассадку
  прежнего сценария. После выхода ручная сверка сдачи и возврат в
  **normal** используют зафиксированный кортеж завершённого Guest.
  Новый Guest получает свою строку состояния и свой ключ. Старое
  подтверждение или команда к новому Guest не переходит.

## Что проверено на Linux

Использовались реальные Squid 7.8, Nginx 1.30.7, OpenSSL 4.1 и Gateway
2692e56b с проверкой настоящих RSA/JWT. Все listener слушали loopback
на случайных портах. Moodle signing, PL callback/Bridge и текущее
состояние контроллера представляли синтетические данные и обработчики.
Прежние рабочие процессы и VM не участвовали в этой пробе.

| Проба | Наблюдение |
| --- | --- |
| Два клиента с одним TCP-адресом на Squid | Для A и B получены разные подтверждённые UID и кортежи в модели. |
| Переход на второй порт и назад | До handoff дошла host-only cookie. PL callback в фикстуре получил базовый Host и вернул браузер на базовый порт. |
| Нет сертификата, неподтверждённый serial или подставленный браузерный заголовок | Синтетический учебный маршрут завершился без записи имени. |
| Другой удостоверяющий центр | Nginx отклонил предъявленный сертификат, привязка отсутствовала. |
| Неверный JWT, отсутствие browser cookie, повтор handoff | Пробы отклонены перед новой записью. |
| Неожиданные Host и SNI | Второй listener не пропустил эти запросы. Прямой private path и маршруты вне handoff закрыты. |
| Выход A и новый Guest A2 | Валидный TLS A1 продолжал соединяться. Текущее соответствие после выхода и нового Guest отклоняло A1. Привязка A2 и неизменный B подтверждены в модели. Новый boot исключил прежнюю привязку A2. |
| Обычный вход преподавателя | Исходный порт успешно провёл его до учебного пути фикстуры без назначения места. |
| Ключ другого клиента | Открытый сертификат A1 не прошёл с закрытым ключом B1. |

Защищённые сценарий и результаты хранятся в каталоге кампании
**.local/contract-vm-20261124**. Для запуска нужен Python из существующего
Gateway окружения, его каталоги **src** и **tests** в **PYTHONPATH**, а
также nginx, squid с **security_file_certgen**, openssl и возможность
открыть локальные listener. Ключи и TLS каталоги создаются на один запуск
и удаляются при завершении. Для цепочки Squid 7.8 отключена дополнительная
строгая проверка X.509 полей OpenSSL в тестовом клиенте из-за динамического
leaf без AKI. Разрешены только два временных issuer и проверка DNS-имени
сохранена. На двух настоящих Windows и с новым портом реального
Moodle/PL приёмка ещё предстоит.
