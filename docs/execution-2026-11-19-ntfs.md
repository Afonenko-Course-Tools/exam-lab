# Результаты файловой пробы 19 ноября 2026 года

На одноразовой Windows VM проверено ограничение чтения для точного SID нового
Shared PC Guest. Сценарии и порядок приведены в [инструкции файловой пробы](windows-ntfs-canary.md).
Оператор выбирал плитку Guest, подтверждал стандартный интерактивный токен и
сохранял управление во время проверки. Правила ставились только на созданные
пробой файлы и каталоги. В проверку вошёл отдельный виртуальный том T: на 2 ГиБ,
который Windows определила как фиксированный NTFS.

## Первые две попытки

Первый `Prepare` завершился в 15:53:10 по Минску за 1332 мс. Из настоящего
Guest все пять маркеров читались из .NET и Java. Win32-проверка дала отказ на
42 из 45 запросов прав мутации. Три открытия прошли с кодом 0. У
`C:\Users\Public\Documents` прошли `DELETE` и `FILE_DELETE_CHILD`, у вложенного
каталога пробы прошёл `DELETE`. Объекты не удалялись. Оператор остановил Apply
до первой записи ACE. Права `CommonDocuments` сохранились. Соседний корень
`C:\Users\Public` при этой проверке дал код 5 для обоих прав.

Во второй попытке новый маркер создали непосредственно под `%PUBLIC%`. В 15:58:25
`Prepare` завершился за 1170 мс. Новый Guest прочитал пять маркеров, 43 запроса
прав мутации получили код 5. Намеренно прерванный `Apply` добавил один запрет
корневому файлу, после чего .NET и Java дали отказ для него и разрешили чтение
других четырёх. `Normal` удалил свой ACE и остановился со статусом `FAIL` на
строгой проверке SDDL. Windows добавила флаг `SE_DACL_AUTO_INHERITED`
(`D:P` → `D:PAI`), сохранив владельца, группу, упорядоченные ACE и содержимое.
Отдельное чтение из этого же Guest снова прошло для всех пяти файлов. Запись
намерения и синтетические маркеры этой попытки сохранены для разбора.
[Автоматическое распространение ACE](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces).

## Повтор на новых маркерах

Третья версия использовала ещё один новый GUID. При `Prepare` она записала уже
установленные права `Users` на девять новых объектов, затем нативно подтвердила
флаги DACL `P` и `AI` до сохранения исходной SDDL. Логика Apply и Normal сохранила
строгое сравнение SDDL. В область пробы вошли контрольные файлы в корне системного
диска, обычном профиле, под `%PUBLIC%`, в `ProgramData` и на T:. Обычный учебный
файл и существующие родительские каталоги в эту область не входили.

`Public\Documents` с правами удаления, объекты с исходным `D:P`, полный набор
данных на C: и автоматический допуск остаются открытыми условиями. Строгий цикл
подтверждён для синтетических объектов с исходным `D:PAI`. Охват будущих файлов
относится к обычному наследованию внутри четырёх каталогов пробы. `FullReady=false`.

## Кандидат до входа

Ранее в проекте исследовался условный `DENY FILE_READ_DATA` для `Users` с
исключением стабильной группы обычных пользователей, необходимых
администраторов и SYSTEM. Этот подход позволяет поставить запись до выбора
плитки Guest. В опубликованных нативных протоколах пока есть только опыты с
точным SID уже вошедшего Guest. `FileSystemAccessRule` не хранит условие callback
ACE. Для пробы нужен подтверждённый writer, который удаляет из текущей DACL
только совпавшую запись по типу, маске, флагам, SID и байтам условия. Снять все
запреты `Users` было бы изменением сторонней политики.
[Исходная архитектурная оценка](file-isolation-options-2026-11-16.md#2-conditional-ace-ordinary-исключён-без-привязки-к-guest-sid),
[условные ACE Windows](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-definition-language-for-conditional-aces-).

Минимальный отдельный тест использует один защищённый синтетический файл на T:.
До появления Guest проверяются исходные разрешения, ставится один условный ACE,
затем исходное чтение проверяют в свежем обычном токене с группой исключения,
в административном токене и от SYSTEM. Первые чтения двух последовательно
созданных Guest должны дать явный отказ при той же записи. После выхода второго
Guest выполняется офлайн-снятие одной записи со сверкой исходной SDDL, File ID,
хеша и чтения обычным пользователем. Наследование, новые данные и полный охват
остаются отдельными фазами. Проверка одного условного ACE не подтверждает
сохранность всех обычных токенов, новых учёток и рабочего профиля Guest.
