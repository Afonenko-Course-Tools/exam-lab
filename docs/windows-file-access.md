# Доступ к локальным файлам: проверка MIC

15 ноября 2026 года на настоящей одноразовой Windows проверен узкий механизм
Mandatory Integrity Control (MIC). Независимая проверка приняла результаты
пяти файловых проб. Готовность файловой политики экзаменационного сеанса
этим испытанием не устанавливается.

## Целевое разделение

Экзаменационному пользователю нужны системные файлы, установленные инструменты
и собственная рабочая область. Данные других пользователей и подсказки,
заранее сохранённые через обычную учётную запись, должны быть закрыты широким
структурным механизмом. Хрупкие списки отдельных пользовательских каталогов
не соответствуют [требованиям](requirements.md#локальные-файлы-и-заранее-подготовленные-подсказки).
Подмена студентом системных файлов исключена из принятой модели угроз.

По документации Microsoft, MIC сопоставляет уровень целостности процесса
с обязательной меткой объекта. Обычная политика `NW` (`NoWriteUp`) запрещает
запись снизу вверх. Для запрета чтения предусмотрена отдельная политика `NR`
(`NoReadUp`) в метке объекта. Сам уровень Low не включает общий запрет чтения
файлов Medium. См. [описание MIC](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)
и [обязательную метку объекта](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-system_mandatory_label_ace).

## Что проверено

Стенд: Windows 10 Enterprise Evaluation 22H2 x64, сборка **19045.2006**,
интерфейс **en-US**, Windows PowerShell 5.1. Это не проверка русской Windows
или Windows 11.

После обычного графического входа один стандартный пользователь выполнил две
пробы. SID пользователя совпал в обоих отчётах; полный SID не публикуется.
Фактические уровни token, прочитанные через `whoami /groups`:

| Проба | Integrity SID | IL | Администратор |
| --- | --- | --- | --- |
| Medium | `S-1-16-8192` | 8192 | Нет |
| Low | `S-1-16-4096` | 4096 | Нет |

В обеих пробах отсутствовало членство в Administrators, включая deny-only.
Для запуска использовались две приватные побайтовые копии штатного CMD
с метками Medium и Low. Метка исполняемого файла сама по себе не считалась
доказательством: чтение начиналось только после проверки SID, nonadmin и
фактического IL дочернего процесса PowerShell.

Все данные находились в одном уникальном тестовом каталоге. Файловые DACL
разрешали этому пользователю чтение. Передача `NR` родительскому каталогу
и перенос файла выполнялись только внутри этой области.

| Случай | Фактическая метка файла | Medium | Low |
| --- | --- | --- | --- |
| Обычный файл | Medium, `NW` | Чтение | Чтение |
| Файл с явным `NR` | Medium, `NW,NR` | Чтение | Отказ |
| Новый файл после установки наследуемого `NR` родителю | Medium, унаследованные `NW,NR` | Чтение | Отказ |
| Уже существовавший файл с явной меткой Medium `NW` | Medium, `NW` сохранилась | Чтение | Чтение |
| Файл с явной меткой Medium `NW`, перенесённый внутри тома к родителю с `NR` | Medium, `NW` сохранилась | Чтение | Чтение |

Каждое успешное чтение совпало с исходным SHA-256 содержимого. Оба отказа Low
содержали `UnauthorizedAccessException`, HRESULT `0x80070005`. Собственная
рабочая область Low успешно записывалась и читалась в обеих пробах.
Метки семи объектов, включая две копии CMD, отдельно прочитаны штатным
[`icacls`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls).
Строковое представление меток диагностического helper оказалось неполным
и не использовалось для вывода о метках.

Оригинальный системный CMD сохранил SHA-256 до подготовки, после проб и после
удаления тестовой области. Системные и обычные пользовательские каталоги
не перемечались. Приватные тестовые каталоги удалены после сохранения результатов;
обычный пользователь остался в сеансе.

## Граница результата

На этом стенде Low совместно с фактическим `NR` запретил чтение. Наследуемая
метка сработала для нового файла. Существующий файл с явной меткой и файл,
перенесённый внутри тома, сохранили `NW` и остались читаемыми. Это наблюдение
двух конкретных случаев; оно не означает, что наследование никогда не действует
на существующие данные. Microsoft отдельно описывает
[правила наследования ACE, общие для DACL и SACL](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules).

Результат уточняет условия применения MIC. Широкий охват существующих данных,
всего сеанса Guest и всех путей запуска ещё требует решения и проверки.
Explorer, IDEA, Java и Git под Low здесь не принимались. Перед выбором файловой
политики нужно подтвердить структурное разделение данных, совместимость
инструментов и сохранность обычных занятий. MIC остаётся исследуемым кандидатом.

## Готовый кандидат: Sandboxie Privacy Mode

По документации и исходникам выпуска
[Sandboxie Plus 1.18.8 / Classic 5.73.8](https://github.com/sandboxie-plus/Sandboxie/releases/tag/v1.18.8)
готовым кандидатом для широкого разделения является
[Privacy Mode](https://sandboxie-plus.github.io/sandboxie-docs/PlusContent/privacy-mode/).
Он скрывает существующие данные вне системной области, позволяет читать Windows,
установленные программы и системную область Microsoft в ProgramData, а новые
рабочие файлы создаёт внутри песочницы. Это штатная исходная политика;
совместимость её шаблонов с нашим учебным окружением ещё не проверена.

Директивы доступа работают с шаблонами путей и Shell Folders.
[`ReadFilePath`](https://sandboxie-plus.github.io/sandboxie-docs/Content/ReadFilePath/)
открывает чтение, а
[`OpenFilePath`](https://sandboxie-plus.github.io/sandboxie-docs/Content/OpenFilePath/)
также разрешает непосредственную запись вне песочницы. Эти параметры не выражают
условие «владелец файла совпадает с SID экзаменационного пользователя».

Для текущей учётки есть штатное сочетание
[`Enabled=y,<имя учётки>`](https://sandboxie-plus.github.io/sandboxie-docs/Content/Enabled/)
и универсального `ForceProcess=*`. Перед применением имя нужно сверить с SID
настоящего текущего Guest; при следующем Guest это соответствие проверяется снова.
В [драйвере выпуска 1.18.8](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/drv/process_force.c#L1078-L1140)
фильтр учётки применяется до правил принудительного запуска. Это кандидат
для новых процессов без перечня отдельных приложений. Уже работающий Explorer
сам в песочницу не переносится; исключения компонентов Sandboxie и маршруты
запуска вне box ещё требуют проверки. Изолированная Java-программа не доказывает
охват всего Guest-сеанса.

У технической оценки есть два разных режима:

| Проба | Условия по источникам 1.18.8 |
| --- | --- |
| Без сертификата | Email и аккаунт не нужны, но драйвер планирует завершение процессов с соответствующими функциями через пять минут. |
| Пробный сертификат на десять дней | Клиент запрашивает email и отправляет имя и HWID онлайн. Отдельной регистрации аккаунта в этом клиентском пути нет; фактическая выдача не проверялась. |

Пятиминутный предел задан в
[коде драйвера](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/drv/process.c#L714-L745).
Длительность продолжительной пробы определена в
[SettingsWindow.h](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/SandboxiePlus/SandMan/Windows/SettingsWindow.h#L239-L240),
запрос email — в
[SettingsWindow.cpp](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/SandboxiePlus/SandMan/Windows/SettingsWindow.cpp#L3133-L3150),
а передача имени и HWID — в
[OnlineUpdater.cpp](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/SandboxiePlus/SandMan/OnlineUpdater.cpp#L287-L331).
Ограниченная оценка описана в
[LICENSE.Plus](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/LICENSE.Plus);
для образовательной эксплуатации документация отдельно требует
[Business Certificate](https://sandboxie-plus.github.io/sandboxie-docs/Content/FeatureComparison/).

В отдельной Windows canary установка 1.18.8 с проверенной подписью прошла;
служба и драйвер работали. До политики обычный пользователь через Java читал
два внешних маркера и JDK, записывал и читал свой workspace. После применения
минимального принудительного запуска для этой фиксированной учётки новый вход
дал чёрный рабочий стол и `SBIE2327 Error in COM server: [31 / 258]`.
Explorer и Java не появились; причина отказа не установлена. Отрицательный
результат независимо проверен, стенд штатно выключен с сохранением диска.

В исходниках 1.18.8 [`LogErr`](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/svc/comserver.cpp#L1355-L1364) выводит коды в формате `%02X / %d`.
`0x31` обозначает [запрос COM class factory](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/svc/comserver.cpp#L258-L286), а `258` — [`WAIT_TIMEOUT`](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitformultipleobjects)
при [ожидании ответа прокси](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/svc/comserver.cpp#L1083-L1132) со [штатным пределом 30 секунд](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/svc/comserver.cpp#L43-L50).
Это локализация симптома; причина зависания остаётся неизвестной.
Следующий диагностический шаг — штатные [`ClsidTrace`](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/dll/com.c#L1416-L1419) и [`NotifyForceProcessEnabled`](https://github.com/sandboxie-plus/Sandboxie/blob/v1.18.8/Sandboxie/core/drv/process_force.c#L419-L421),
с сопоставлением CLSID, PID и времени, без добавления исключений доступа.

Одна дополнительная диагностическая попытка включила только эти два trace-параметра.
В новом ordinary-сеансе штатное окно Task Manager не появилось; до Monitor и
экспорта Trace Log дойти не удалось, CLSID не получен. Наблюдалось сообщение
`SBIE2224` о сбое Explorer. Связь этого сбоя с COM-таймаутом не установлена.
VM штатно выключена; исключения доступа и дополнительные launchers не добавлялись.

Поэтому чтение внешних файлов, JDK и workspace под этой политикой не проверены.
Охват всего Guest-сеанса, IDEA/Git и дочерних процессов, сохранность обычных
занятий и очистка не приняты. Проба фиксированной учётки не проверяет жизненный
цикл Shared PC Guest; пятиминутная оценка не является экзаменационным режимом.
