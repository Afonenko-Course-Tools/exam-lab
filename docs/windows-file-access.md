# Доступ к локальным файлам: проверка MIC

15 ноября 2026 года на настоящей одноразовой Windows проверен узкий механизм
Mandatory Integrity Control (MIC). Независимая проверка приняла результаты
пяти файловых проб. Готовность файловой политики экзаменационного сеанса
этим испытанием не устанавливается.

## Целевое разделение

Экзаменационному пользователю нужны системные файлы, установленные инструменты
и собственная рабочая область. Данные других пользователей и подсказки,
заранее сохранённые через обычную учётную запись, должны быть закрыты широким
структурным механизмом. Хрупкие списки отдельных пользовательских каталогов
не соответствуют [требованиям](requirements.md#локальные-файлы-и-заранее-подготовленные-подсказки).
Подмена студентом системных файлов исключена из принятой модели угроз.

По документации Microsoft, MIC сопоставляет уровень целостности процесса
с обязательной меткой объекта. Обычная политика `NW` (`NoWriteUp`) запрещает
запись снизу вверх. Для запрета чтения предусмотрена отдельная политика `NR`
(`NoReadUp`) в метке объекта. Сам уровень Low не включает общий запрет чтения
файлов Medium. См. [описание MIC](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)
и [обязательную метку объекта](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-system_mandatory_label_ace).

## Что проверено

Стенд: Windows 10 Enterprise Evaluation 22H2 x64, сборка **19045.2006**,
интерфейс **en-US**, Windows PowerShell 5.1. Это не проверка русской Windows
или Windows 11.

После обычного графического входа один стандартный пользователь выполнил две
пробы. SID пользователя совпал в обоих отчётах; полный SID не публикуется.
Фактические уровни token, прочитанные через `whoami /groups`:

| Проба | Integrity SID | IL | Администратор |
| --- | --- | --- | --- |
| Medium | `S-1-16-8192` | 8192 | Нет |
| Low | `S-1-16-4096` | 4096 | Нет |

В обеих пробах отсутствовало членство в Administrators, включая deny-only.
Для запуска использовались две приватные побайтовые копии штатного CMD
с метками Medium и Low. Метка исполняемого файла сама по себе не считалась
доказательством: чтение начиналось только после проверки SID, nonadmin и
фактического IL дочернего процесса PowerShell.

Все данные находились в одном уникальном тестовом каталоге. Файловые DACL
разрешали этому пользователю чтение. Передача `NR` родительскому каталогу
и перенос файла выполнялись только внутри этой области.

| Случай | Фактическая метка файла | Medium | Low |
| --- | --- | --- | --- |
| Обычный файл | Medium, `NW` | Чтение | Чтение |
| Файл с явным `NR` | Medium, `NW,NR` | Чтение | Отказ |
| Новый файл после установки наследуемого `NR` родителю | Medium, унаследованные `NW,NR` | Чтение | Отказ |
| Уже существовавший файл с явной меткой Medium `NW` | Medium, `NW` сохранилась | Чтение | Чтение |
| Файл с явной меткой Medium `NW`, перенесённый внутри тома к родителю с `NR` | Medium, `NW` сохранилась | Чтение | Чтение |

Каждое успешное чтение совпало с исходным SHA-256 содержимого. Оба отказа Low
содержали `UnauthorizedAccessException`, HRESULT `0x80070005`. Собственная
рабочая область Low успешно записывалась и читалась в обеих пробах.
Метки семи объектов, включая две копии CMD, отдельно прочитаны штатным
[`icacls`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls).
Строковое представление меток диагностического helper оказалось неполным
и не использовалось для вывода о метках.

Оригинальный системный CMD сохранил SHA-256 до подготовки, после проб и после
удаления тестовой области. Системные и обычные пользовательские каталоги
не перемечались. Приватные тестовые каталоги удалены после сохранения результатов;
обычный пользователь остался в сеансе.

## Граница результата

На этом стенде Low совместно с фактическим `NR` запретил чтение. Наследуемая
метка сработала для нового файла. Существующий файл с явной меткой и файл,
перенесённый внутри тома, сохранили `NW` и остались читаемыми. Это наблюдение
двух конкретных случаев; оно не означает, что наследование никогда не действует
на существующие данные. Microsoft отдельно описывает
[правила наследования ACE, общие для DACL и SACL](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules).

Результат уточняет условия применения MIC. Широкий охват существующих данных,
всего сеанса Guest и всех путей запуска ещё требует решения и проверки.
Explorer, IDEA, Java и Git под Low здесь не принимались. Перед выбором файловой
политики нужно подтвердить структурное разделение данных, совместимость
инструментов и сохранность обычных занятий. MIC остаётся исследуемым кандидатом.
