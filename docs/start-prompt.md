# Стартовое поручение для исполнительной сессии

Начинаем реализацию `exam-lab` на этом Linux-ноутбуке с большей доступной RAM.
Docker и KVM/QEMU уже настроены. Это исполнительная сессия: переходи от проверки
условий к подготовке Windows VM, реализации и испытаниям.

Репозиторий: https://github.com/Afonenko-Course-Tools/exam-lab.
Если локальной копии нет, клонируй его. Прочитай применимые `AGENTS.md`, README,
`docs/requirements.md`, `docs/work-plan.md`, `docs/source-review.md` и задачи #1–2.
Согласованные требования сохраняются; уточняй только действительно недостающие данные.

Соблюдай пользовательские ограничения на модели: только `gpt-6.1-sol` и
`gpt-6.1-terra` с явно назначенным усилием, Standard, без изменения глобальной
конфигурации. Координацию исполнения и технический Windows-пилот поручай
`gpt-6.1-sol` с `reasoning_effort="high"`; независимую техническую проверку —
другому `gpt-6.1-sol` с тем же усилием. Применимые требования допуска проверяй
по действующим пользовательским инструкциям целевой сессии. Старые сроки,
очереди и учебные поручения других проектов не возобновляй.

## Первый результат

Подготовь эталонную Windows VM и небольшой локальный пилот: настоящий Shared PC
Guest, запрет чтения файлов с флешки, обязательные сетевые ограничения и локальное
завершение экзамена преподавателем/администратором без сервера. После работоспособного
пилота добавь повторные автоматические проверки на одноразовых копиях эталона.
Контроллер и исходящий опрос — следующий этап после проверки этого пути.

## Порядок работы

1. Проверь состояние репозитория, ресурсы ноутбука и фактический доступ к Docker,
   KVM/QEMU/libvirt. Ошибку внутри песочницы не считай доказательством отсутствия
   инструмента на хосте: используй предусмотренный механизм доступа и подтверждай
   результат. Сохраняй чужие ВМ, контейнеры, рабочие деревья и данные.
2. Сам найди доступный официальный образ или ISO подходящей Windows 10, создай
   VM и установи Windows штатными средствами автоматической установки. Готовой
   Windows VM и ISO пока нет; заранее устанавливать Windows пользователю не нужно.
   Требуемый вход владельца или подтверждение лицензии выдели в один конкретный
   ручной шаг. Не подменяй целевую desktop Windows контейнером или другой ОС без
   согласования. Зафиксируй фактические редакцию и сборку.
3. Настрой технический доступ к гостевой системе, установи согласованные IDEA,
   JDK и Git, подготовь эталон. Изменяемые экзаменационные настройки проверяй
   на отдельной одноразовой копии Windows, не на рабочем Linux-хосте.
4. Найди переданный `exam-lab-0.1.0.zip` и используй разбор поставки для адресного
   переиспользования. Если архив не перенесён, запроси его местоположение,
   продолжая независимую подготовку VM. Не переноси автоматически всю старую
   инфраструктуру, широкий PnP-запрет и постоянные изменения общих каталогов.
5. Начни с одного PowerShell-модуля и одного входа для проверки, включения
   и локального завершения. Реализуй сохранение и восстановление исходных значений,
   проверку фактического результата, безопасные повторы и обработку частичного отказа.
6. Проведи реальные Windows-проверки. После работоспособного пилота добавь одну
   небольшую обвязку QEMU/libvirt для временной копии, запуска проверок, сохранения
   обычного отчёта и завершения только своей тестовой VM.

## Обязательные проверки

- Настоящий новый Shared PC Guest получает ограничения; после выхода следующий
  Guest получает чистый профиль. Обычные профили и учебные файлы сохраняются.
- Guest не читает подсказку с флешки через Explorer, IDEA и Java; проверяются
  новый, ранее использованный и заранее вставленный носитель. В обычной учётке
  USB остаётся работоспособным. Виртуальный USB не заменяет физическую проверку.
- Разрешены только согласованные PrairieLearn, Moodle `https://edurfe.bsu.by/`
  и подтверждённые технические назначения. Посторонние соединения блокируются
  также из Java; проверяются используемые IPv4/IPv6 и ранее открытое соединение.
- Для Moodle проверь полный маршрут входа и сдачи в чистом браузере. Обнаруженные
  ранее Google Tag Manager и внешние шрифты не добавляй автоматически в разрешения.
  Адрес конкретного PrairieLearn и неизвестные зависимости уточни до утверждения
  окончательных сетевых правил; независимые локальные пробы продолжай.
- Локальное завершение работает без контроллера и восстанавливает обычные занятия.
  Guest не может снять ограничения или изменить управляющие сценарии. Его выход
  очищает профиль, сохраняя экзаменационный режим для следующих студентов.
- Ошибка опроса ничего не меняет; потеря связи сама не снимает экзамен. После
  локального завершения прежний серверный `exam` не должен включить режим снова.
  В этом пилоте зафиксируй этот договор для будущего контроллера, не строй его заранее.

## Границы автоматизации

Используй готовые средства Windows, PowerShell, планировщик и QEMU/libvirt.
Не создавай собственные пакетные менеджеры, форматы блокировки зависимостей,
универсальные обновляторы, очереди, протоколы доказательств и фабрику образов.
Повторная установка с ISO и робот для визуального входа при каждом прогоне не нужны.

Работай автономно в принятом объёме. Реализуй и проверь всё доступное до запроса
ручного шага. Для настоящего Guest/IDEA, входа в Moodle и физических USB допустимы
короткие ручные проверки на первом пилоте и после существенных изменений.
Пока ожидается ручная проверка, продолжай независимую работу; неизвестный результат
оставляй непроверенным. Проверки с подменёнными API не объявляй испытаниями Windows.

Если USB-политика или восстановление не проходят реальную пробу, разберись с этим
конкретным механизмом до расширения проекта. Изменение требований согласуй по
конкретному результату пробы. Доступ к Proxmox и аудиторным ПК для текущего пилота
не требуется; развёртывание на них выполняется отдельным этапом.

## Сохранение результата

Работай в ветке `codex/…`. Код и тесты поручай техническому исполнителю;
независимую проверку выполняет другой агент. У каждого файла в одной фазе один владелец.
Коммиты, push и черновик PR с реализацией этого объёма разрешены; сохрани инструкции
воспроизведения, результаты выполненных проверок и небольшой список оставшихся
ручных действий. Не сливай реализацию в основную ветку и не распространяй её на класс
вместо локального пилота. Отчёт и новая документация — по-русски.

Начни с проверки окружения и подготовки Windows VM, затем выполняй локальный пилот.
