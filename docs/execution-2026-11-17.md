браузера до origin не сохраняется; этот более сложный путь отложен.

Выбранный пакет: optional audit после verified student LTI selected activity,
серверный examId, verifiedUID/displayName и доверенный источникIP; монитор

LTI-входа. Неизвестный/недоверенный источник не разрешается в строгом режиме.
Обычный LTI вне этой activity не меняется. AuditDBfailure не ломает обычный вход;
сам CIDR-gate не зависит от успешной записи журнала.

Источник должен производиться готовыми средствами: Squid очищает клиентский XFF
и передаёт фактический IP, Nginx доверяет только явно заданному прокси, перезаписывает
приватные gateway-заголовки. Real-IP модуль и сквозной TLS/бамп-путь ещё проверяются.
10/8 — диапазон допуска клиентов, не список доверенных прокси. Сырой заголовок
браузера или IP Squid нельзя объявлять адресом рабочего места.

Автор Gateway — gateway_monitor_impl, независимый reviewer — gateway_monitor_review;
оба явно назначены Sol/high. Транспортный source-автор — gateway_infra_read.
Gateway находится в отдельном checkout/ветке codex/exam-pc-identity; pinned Platform
не редактируется. Productionwrite/restart/DB/studentlogin в текущем пакете не делаются.
Сопоставление IP не считается аппаратной идентичностью ПК, подтверждением Guest,
посещаемости или контролем старой открытой PL-сессии.

### Цена широкой ACL-области и проверка простоты

Одна read-only inventory заняла8.625s:2471 посещённый объект,1366 файлов-кандидатов,
из них237 принадлежат двум configured ordinary SID,99 имеют protected DACL,
147 имеют несколько hardlinks. Точки reparse не обходились; встречались ошибки
чтения ACL/информации. Отсутствие срабатывания лимита не означает полное покрытие.
Ownership не равно эффективному праву записи: выбор только ordinary-owned файлов
не закрывает подсказки в доступных для записи файлах другого владельца.

Частный writer занимает186 строк, не имеет per-program правил и меняет ACL через
один icacls /deny exactGuestSID:(RD) на файл. Остальное — preflight, адресный учёт
своих изменений и проверка сохранности metadata. Его лимиты200 файлов/каталогов
и пофайловая перезапись pending сделаны для небольшой пробы; их нельзя просто
снять и назвать готовой широкой реализацией. ProgramData содержит общие ресурсы,

### Следующая фаза по выбору владельца: AppContainer

Владелец отдельно задал клиентский предел: x64, обычно8ГБRAM, без виртуализации

Базовый AppContainer — изоляция процессов средствами Windows8+, без отдельной ОС
и Hyper-V. Не следует смешивать его с современным Win32 app isolation, требования
которого ориентированы на новые Windows11. Windows Sandbox требует виртуализации;
Windows Containers не дают нужный интерактивный desktop и не выбираются.
Первичные источники: [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer),
[Win32 app isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/app-isolation-overview),
[Sandbox](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-install),
[Windows Containers](https://github.com/MicrosoftDocs/Virtualization-Documentation/blob/main/virtualization/windowscontainers/quick-start/lift-shift-to-containers.md).

Первый критерий нового эксперимента — настоящий ограниченный Guest запускает
IDEA в настоящем AppContainer, работает в отдельном чистом каталоге, собирает Java,
запускает дочернюю JVM и отлаживает. Проверяются фактические токены IDEA и потомков,
доступ к рабочему каталогу и отказ чтения внешней подсказки, а не одно название
launcher. Предпочтителен готовый OSS-инструмент либо небольшая native-обвязка.

нового драйвера или перечня отдельных системных EXE/COM-исключений.

Изоляция одной IDEA пока **не** закрывает Explorer/Notepad вне контейнера и не
заменяет весь Guest-путь. Этот обход исследуется отдельно; успешная IDEA не будет
объявлена FullReady. Накладные расходы и работоспособность IDEA в AppContainer
