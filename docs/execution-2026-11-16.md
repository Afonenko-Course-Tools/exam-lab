## Уточнение задачи и архитектурная ревизия

Владелец уточнил: файловое ограничение должно быть широким и простым,
строгость может быть умеренной; нужно проверять близкие варианты. Поэтому
следующий шаг — штатный Shared PC `RestrictLocalStorage`, отдельно от отладки
Sandboxie и массовой переметки файлов. Списки исключений отдельных программ,
новые launchers и собственный механизм изоляции не добавляются.

Microsoft описывает `RestrictLocalStorage` как ограничение просмотра и сохранения
локальных данных через File Explorer. Свойство
[`ShouldAvoidLocalStorage`](https://learn.microsoft.com/en-us/uwp/api/windows.system.profile.sharedmodesettings.shouldavoidlocalstorage)
сообщает приложениям о необходимости скрыть точки доступа; Downloads, removable
и mapped drives описаны как исключения. Это описание интерфейса, а не доказанный
запрет Java API. Для canary планируется сравнить Explorer, IDEA File Open и Java
на известных контрольных файлах, сохранить работу JDK и собственного workspace,
затем проверить обычную учётку после снятия ограничения. По
[CSP SharedPC](https://learn.microsoft.com/en-us/windows/client-management/mdm/sharedpc-csp#restrictlocalstorage)
политика задаётся до включения Shared PC, поэтому используется свежая копия эталона.

Соседний простой вариант — пользовательская `NoViewOnDrive`: Microsoft явно
[не обещает запрета другим программам](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-windowsexplorer#noviewondrive).
Его следует оценивать как ограничение интерфейса, включая возможную помеху своему
workspace. MIC Low без объектного NR уже позволил чтение; массовая установка NR
не выбрана. Sandboxie сохраняется как отдельный кандидат после двух отрицательных
проб; продолжение COM-диагностики не является первым шагом по новому приоритету.

## Параллельные проверки

- Русская MUI: подготовлена пара новых GUI PowerShell при реальных консольных
  CP437 и CP866. Проверяется гипотеза языкового fallback без SetCulture,
  подмены Thread UI и изменения языковых списков. Результат пары приведён ниже.
- Общий Guest USB/network: независимо проверен план с прямыми публичными
  компонентами, временными CU CA/proxy и локальным GUI-вызовом исходной SYSTEM
  normal-задачи. До USB Apply все nonadmin-профили должны быть выгружены;
  перед общим normal нужны CU Cleanup, выход Guest и выгрузка профиля.
  Сценарий пока не выполнялся. Контроллер и миграция рабочего сервера не расширяются.

## Нативные результаты

### Русская MUI: CP437 и CP866

В одной настоящей GUI CMD `/d` последовательно запущены два новых Windows
PowerShell NoProfile. Нативные API подтвердили фактические CP437 и CP866,
общего родителя и разные дочерние PID; оба reader завершились успешно.
Естественные UI-культуры PowerShell/Host/CLR остались en-US в обоих случаях.
Пользовательский список языков сохранился `ru, en-US`. В этой паре смена кодовой
страницы не объяснила fallback. Это отрицательный результат, а не русская
совместимость: Prepare Check не вызывался, новые языковые setters не применялись.
Артефакты независимо проверены; копия15990 штатно выключена, эталон сохранён.

Первая попытка ввода CMD была остановлена проверкой аргументов до MUI API:
диагностический QMP helper пропустил символ `/`. Она не входит в пару результатов.
Исправленный явный ввод `/d` подтверждён перед двумя действительными запусками.

### Сохранность стенда и сетевой контроль

Вчерашняя браузерная VM15989 штатно выключена после выхода обычного пользователя,
без Force. Перед выключением свежие native-чтения подтвердили CA0, исходные
WinINET flags9 с пустыми proxy/PAC/bypass, own GPO0 и18 NotConfigured, отсутствие
работающих собственных задач и прежние хеши двух учебных файлов.

Готовый Squid запущен с прежними образом, конфигурацией, CA и приватным state,
без изменения системного доверия. Однократные Linux-контроли дали PL302,
Moodle303 и собственный foreign Host403, client TLS verify0. Это проверка
готовности прокси перед новым Guest-циклом, не приёмка Windows-сети.

Остальные перечисленные выше эксперименты ещё выполняются. Подготовка стенда
и принятые исходники сами по себе не означают успешного выполнения Windows-проб.
