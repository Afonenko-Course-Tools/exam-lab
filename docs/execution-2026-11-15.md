# Исполнительная сессия 15 ноября 2026 года

Работа ведётся в ветке `codex/windows-local-pilot`. Это отчёт о фактическом
состоянии локального пилота, а не разрешение на внедрение в аудитории.

После архитектурной ревизии владелец уточнил договор: Shared PC допускается
подготовить однократно при сохранности обычных занятий, а экзаменационный
переключатель работает без снимков Windows и полного импорта firewall/GPO/реестра.
Приведённые ниже snapshot/restore-пробы относятся к прежнему эксперименту,
который больше не развивается и не включён в опубликованную поставку.
Новый минимальный переключатель пока не принят. Копии VM служат испытательным
стендом; они не являются способом завершения экзамена на аудиторном ПК.

Прежняя VM `exam-lab-guest-pilot` штатно выключена в 14:55 UTC; её диск и
диагностика сохранены, старый finish/import больше не вызывается. Для нового
механизма запущена отдельная чистая копия эталона `exam-lab-owned-settings`
(WinRM 15988, VNC 5908). Независимая проверка в 15:02 UTC подтвердила отсутствие
пилота и его задач, прежние хеши учебных файлов и обычного пользователя без
административных прав. В 15:14–15:20 UTC новый установщик и единственный SYSTEM
check прошли независимую Windows-проверку: четыре защищённые задачи, точные байты
кода/config, прежние учебные файлы, отсутствие mode/state. Штатный MDM instance
найден. Команда exam ожидаемо отказала; первый prepare остановился до metadata
и настроек: код ошибочно приводил unset/null к числу. Исправленный preflight
принимает только семь unset-полей, а заданные значения требует разбирать отдельно.
В 15:37–15:40 UTC применение конфигурации независимо принято: SharedPC включён,
DeletionPolicy=0, три точных exemptions, roster и учебные файлы сохранены.
Повтор prepare и normal не изменили metadata и настройки; после штатного reboot
их сохранность подтверждена в 15:49 UTC. Guest lifecycle и обычные занятия
этими чтениями ещё не приняты.

Уточнение владельца в этой сессии: основной результат подготовки — устойчивый
воспроизводимый инструмент для уже установленной Windows с проверкой совместимости
в разных версиях. Установка эталона с ISO и разовые диагностические сценарии
служат испытательным стендом. Они не заменяют этот инструмент и не доказывают
поддержку других сборок Windows. Подготовка программ отделена от включения
экспериментальных экзаменационных политик.

Уточнён основной сценарий установки: повышенный административный токен,
проверка минимальных версий и возможностей Windows до изменений, целевая ОС
русскоязычная, все целевые системы x64. Наличие SID и системных путей проверяется в коде; испытание
на английском эталоне с кириллицей в путях отмечается отдельно от русской ОС.

Публикация скриптов и установщиков на локальном сервере по следующему указанию
владельца отложена до ввода VM контроллера. Сейчас проверяется офлайн-каталог
с теми же фиксированными файлами и проверками; сервер PrairieLearn не изменяется.

## Воспроизведение и локальные материалы

См. [подготовку VM](windows-vm.md) и [порядок пилота](local-pilot.md).
Исходные ISO, диски, исходный архив, пароли и диагностические журналы находятся
только в игнорируемом `.local/`. Политики испытываются на копии эталона;
эталон и посторонние ВМ не используются для экспериментальных изменений.
Следующие сетевые и trust-пробы относятся к закрытому прежнему прототипу.

Сертификат CA PrairieLearn проверен отдельно: SHA256 DER
`28:F6:4C:CB:01:A7:4A:B9:DA:08:8D:24:03:E1:67:78:43:6F:35:D1:A0:6B:0E:9A:2F:7C:9E:FB:37:69:CC:2F`.
Глобальный импорт этого CA в Windows Root и JDK cacerts отклонён автоматической
проверкой разрешений и не выполнен: такое действие расширяло бы доверие ко всем
подписанным этим CA именам. Эталон сохраняется без этого изменения. Следующий
кандидат использует сертификат в хранилище конкретного процесса прокси;
необходимое доверие клиентскому сертификату локального TLS-прокси рассматривается
отдельно, после подготовки конкретного сертификата и согласия владельца.
TLS-проверка не отключается, Linux trust store не изменяется. Java использует
собственное хранилище доверия, поэтому TLS-ошибка Java сама по себе не доказывает
блокировку firewall.

На одноразовой копии сгенерирован отдельный публичный сертификат локального
mitmproxy: SHA256 DER
`93:9D:FF:02:88:61:ED:BA:04:B1:AC:2F:C6:33:C7:13:66:30:6C:FB:5D:17:28:55:03:C1:56:BD:EE:A7:CD:F7`.
Независимо проверены CA:TRUE, публичный DER и совпадение отпечатка. Владелец
отдельно разрешил временное доверие только текущего одноразового Guest и отдельного
хранилища тестовой JVM. Последующим указанием владелец также разрешил дальнейшие
операции с сертификатами в рамках проекта; текущая проба сохраняет прежний узкий
набор доверия. На момент последнего readback listener прокси отсутствует.
Native guard сначала остановил импорт из-за неверного вспомогательного SHA1
в старом checkpoint; согласованный SHA256 совпадает. Фактический SHA1:
`5A1D432C157411C8B750977ACDFE6E674A18A9E5`. Затем исправляется несовместимость
атомарной записи вспомогательного журнала с привязкой null в PS5.1. Эти отказы
произошли до trust-операций. После исправления и штатного подтверждения Windows
импорт в CurrentUser Root настоящего Guest прошёл: ровно один согласованный CA,
task result0. Отдельный PKCS12 содержит один публичный trustedCertEntry; Users RX.
Независимый native readback подтвердил неизменность полных LM/admin Root и JDK
cacerts. Последующая очистка независимо принята в 14:16 UTC: точный CA Guest,
отдельный JVM store и собственные trust tasks отсутствуют. Общие LM/admin Root
и JDK cacerts остались прежними; proxy state/process/listener отсутствуют.
Такой CA допускает расшифровку HTTPS и подпись произвольных имён; ограничение
двумя сайтами должен обеспечивать ещё не испытанный прокси с firewall.

Перед сетевой пробой найдено ещё одно фактическое различие: после входа Guest
firewall содержит 468 правил вместо исходных 396 — 72 добавленных, ни одного
удалённого или изменённого исходного правила, профили совпадают. Это независимо
проверено. Причина регистрации Appx/WebView2 пока предполагается. Одноразовый
кандидат был привязан к точному текущему снимку из 468 правил. Его Stop возвращал
этот снимок; прежний finish предполагал возврат исходных 396 правил. Этот механизм
отклонён новым договором и больше не запускается. Исходный GuestOnly baseline
не переписывался.

Три попытки Start не дали работающего сетевого режима. Первая остановилась
до экспорта firewall: тестовые задачи открытых соединений попали под защиту
от параллельных задач управления. Их новый префикс исправлен в обвязке.
Вторая действительно начала отключать правила и затем выполнила откат.
Независимо проверено точное восстановление 468 правил, отсутствие listener,
процессов и активного состояния кандидата; исходный GuestOnly state сохранён.
Исследование выявило отсутствующий обязательный DisplayName в New-NetFirewallRule;
узкая правка установлена и прошла свежий Check. Исторический текст исключения
не сохранился, поэтому совпадение с причиной второго отказа остаётся выводом
из кода и фактических метаданных cmdlet, а не записью того исключения.

Третья попытка также не достигла Running; точная причина не установлена.
Отдельная version-only диагностика подготовлена, но не запускалась после решения
упростить архитектуру. Исходное действие задания и его права восстановлены
и независимо сверены; SDDL отличается только нормализованным флагом AI.
Позднее firewall сам изменился с 468 до 473 правил, включая новые Allow для
приложений. Причина появления правил не доказана; однократное отключение списка
не обеспечивает устойчивого ограничения. Локальная SYSTEM-ветка прокси закрыта
как эксперимент, её обвязки не переносятся в продукт. Собственный host HTTP
контроль на loopback:49200 остановлен после проверки PID и времени создания.

## Общая конфигурация платформы

По новому поручению рассмотрены история курсов и инструментов, актуальные
репозитории и действующая VM PrairieLearn. Подготовлено
[предложение вариантов](work-plan.md#предложение-по-общей-конфигурации-платформы-и-стенда):
расширить существующий prairielearn-local как единственного владельца
развёртывания, сохранив независимость курсов, Platform и exam-lab.
По прямому разрешению владельца репозиторий переименован в
`prairielearn-deployment`; история сохранена. Подготовлен отдельный Compose для
запуска существующих данных и конфигурации без создания Moodle и нового стенда.
Его тесты и независимая проверка пройдены; работающий сервер на него не переводился.
План переноса на новую параллельную VM сохранён в
[документации Deployment](https://github.com/Afonenko-Course-Tools/prairielearn-deployment/blob/codex/unified-deployment/docs/parallel-vm-migration.md).

Фактический рабочий Compose и Nginx на VM совпадают с историческим локальным
bundle, который не хранится в Git; каталог VM не является Git checkout.
Актуальные Local и Platform уже содержат более новые договоры, поэтому
перенос требует сверки, а не копирования старого Compose.
На VM диск 60 GiB, ext4 без LVM, свободно около 6 GiB.
Владелец разрешил увеличение диска и перезапуск при сохранении общей Git-конфигурации.
Доступ к Proxmox с ноутбука и через VM пока не подтверждён; размер диска,
серверные файлы и работающие сервисы в рамках этой оценки не менялись.

## Совместимость подготовки

У согласованного набора программ минимальная предпосылка — x64 Windows 10 1809:
это нижняя граница [IDEA 2025.2](https://www.jetbrains.com/help/idea/2025.2/installation-guide.html).
[Git for Windows](https://gitforwindows.org/requirements.html) текущей выбранной
версии требует Windows 10 или новее. Эти предпосылки не являются результатом
испытаний на каждой промежуточной сборке. В данной сессии проверена только
Enterprise Evaluation 22H2, 19045.2006; другие сборки, редакции и русская локализация
пока не испытаны. Пригодность программ и возможность Shared PC Guest проверяются
раздельно: успешная установка IDEA не доказывает готовность экзаменационной среды.
