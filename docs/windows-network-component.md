# Экспериментальный сетевой компонент Windows

`windows/ExamNetwork.psm1` использует штатные NetSecurity и локальную GPO.
Он пока не включён в основной `exam`: `FullReady=false`, приёмка файловых
ограничений и общего экзаменационного пути остаётся отдельной.

Настройки находятся только в защищённом `pc.json`, в необязательном `Network`:

```json
{"ProxyEndpointIP":"192.0.2.10","ProxyEndpointPort":3128,"TechnicalAccess":[]}
```

Администратор задаёт реальный IPv4 сервера proxy и порт. `TechnicalAccess` —
явный массив технических входящих TCP-разрешений вида
`{"RemoteIP":"192.0.2.20","LocalPort":5985}`. Пустой массив не разрешает удалённое
управление. Адреса PL/Moodle и HTTPS Host-политика принадлежат конфигурации
серверного proxy и в Windows не дублируются.

Необязательный `DhcpServerIP` задаёт буквальный IPv4 одного доверенного DHCPv4
сервера выделенного сегмента. Перед Apply Windows находит маршрут к proxy и
подтверждает действующую Preferred DHCP-аренду от этого сервера на выбранном
интерфейсе. Два правила для службы `Dhcp` в `svchost.exe` разрешают UDP с
локальным портом 68 и удалённым 67. Входящий трафик ограничен адресом сервера,
исходящий также допускает `255.255.255.255` для получения аренды. Конфигурация
без `DhcpServerIP` продолжает требовать один Manual/Preferred IPv4 для Apply.

Компонент поставляется существующим установщиком в `%ProgramFiles%\ExamLab`.
Единственный `pc.json` и `network-owned.json` находятся в защищённом
`%ProgramData%\ExamLab`. Ownership содержит только Schema, RunId,
ComputerIdentity и SHA256 конфигурации; предыдущие настройки Windows не сохраняются.
Изменение конфигурации при существующем intent запрещает продолжение/удаление.

Экспорты: чистая проверка `Test-ExamNetworkConfig`; чтение
`Get-ExamNetworkStatus -Config ... -ConfigRevision ...`; изменение
`Invoke-ExamNetworkUnderLock -Action Apply|Normal` с теми же аргументами и живым
`-OperationLock`. Главный диспетчер заранее открывает общий `operation.lock`
с `FileShare.None`, проверяет все компоненты и вызывает их последовательно.
Компонент не открывает повторный lock. Чтение ничего не создаёт.
`State=NotConfigured` означает отсутствие собственного ограничения;
`Applied` — полный собственный GPO-набор, `Applying` — частичный, `Conflict` —
изменённые/неопознанные собственные данные. `NormalAllowed` и `Blockers`
относятся к снятию. `Get-ExamNetworkStatus -CheckApplyHost` читает предпосылки
Apply до записи, `EffectiveApplied` подтверждает правила и профили ActiveStore.

Экспериментальный Apply испытывается только на отдельной Windows VM. Код проверяет
native AMD64, Windows client 19041+, отсутствие членства в домене и регистрации
у провайдеров управления и работающие BFE/MpsSvc. Адрес, маршрут и аварийный
локальный административный вход готовят отдельно. Перед отключением merge
в ActiveStore проверяются собственные разрешающие правила. Для удалённой пробы
обязательно явно разрешить свой WinRM
peer и иметь локальный административный Normal без сервера.

Собственный набор: Domain/Private/Public `Enabled=True`,
`DefaultInboundAction=Block`, `DefaultOutboundAction=Block`,
`AllowInboundRules=True`, `AllowLocalFirewallRules=False`,
`AllowLocalIPsecRules=False`; один выходящий TCP allow к proxy и по одному
входящему allow на TechnicalAccess; LocalAddress у правил равен Any,
чтобы локальный Normal не зависел от сохранения адреса/линка. Удалённый адрес
и порт всегда точные. В именах правил используется
`ExamLab.Network.*`; все фильтры проверяются перед удалением. Постороннее правило
локальной GPO блокирует Apply и эффективный допуск. Normal сохраняет это правило,
возвращает свои шесть полей в `NotConfigured`, удаляет свои неизменённые правила
и затем intent. Normal не проверяет DHCP-аренду и не обращается к proxy.
PersistentStore не изменяется.
Конфигурация без Network и без intent допускает Normal no-op также на DHCP.

Частный canary на Windows10 подтвердил первый Apply/Normal: новые IPv4/IPv6
сокеты к запрещённому endpoint блокировались, два непрерывных старых сокета
прерывались, добавленный локальный PersistentStore Allow не обходил no-merge;
после Normal связь восстановилась. Независимо проверены сохранность выбранных
исходных правил/профилей PersistentStore и двух обычных файлов. Во втором
Apply штатный batch Set-NetFirewallProfile частично изменил профили и вернул
AccessDenied. Локальный повышенный Normal снял частичный набор при остановленном
proxy; после перезагрузки обычная связь восстановилась. Узкая замена batch-вызова
на последовательные вызовы по одному профилю с `ThrottleLimit 1` прошла два новых
Apply/Normal цикла. Возможная конкуренция CIM остаётся гипотезой причины отказа.
Приёмка частного canary автоматически на публичный модуль не переносится.
Чужой новый Allow при no-merge проверялся отдельно от HTTPS policy.

15 ноября 2026 года публичный `ExamNetwork.psm1` (`3be82e3a…`) отдельно испытан
после штатной установки на свежей Windows VM. До Apply получены настоящие HTTP
200 по IPv4 и IPv6 и CONNECT 200 от разрешённого proxy. Один прямой компонентный
Apply под общим lock подтвердил собственные правила и все 18 полей ActiveStore;
после него новые прямые IPv4/IPv6 сокеты отказали на стадии TCP Connect, а
разрешённый proxy продолжал отвечать CONNECT 200. Это административные TCP-пробы,
не доказательство TLS, Guest или AppContainer изоляции.

После остановки proxy существующее фиксированное SYSTEM-задание общего Normal
запущено через технический WinRM с установленным локальным кодом, без загрузки
с сервера. Свежий результат задания — 0, обе компоненты подтвердили SourceNormal;
сетевые поля стали NotConfigured, собственные правила и intent исчезли.
HTTP 200 по IPv4/IPv6 восстановился. Выбранные поля 437 исходных правил
PersistentStore, его профили и два обычных файла совпали до/после. В этом цикле USB уже был
Normal перед сетевым Apply; совместный USB+Network Applied и GUI-инициация Normal
тогда не проверялись. Частные повторные циклы не заменяют публичную приёмку.

16 ноября на той же VM проведён следующий ограниченный цикл с настоящим новым
Shared PC Guest: прямые вызовы публичных USB и Network компонентов одновременно
оставили обе компоненты Applied. Готовые Java-пробы подтвердили отказ чтения USB
при доступном локальном файле; прямые TCP IPv4/IPv6 до Network Apply были доступны,
после него вернули Permission denied, а TCP к разрешённому proxy остался доступен.
Обычный Edge этого Guest открыл PL и Moodle с проверенными сертификатами, получил
собственный отказ Squid для постороннего адреса, а отдельный Edge с явным
`--no-proxy-server` получил `ERR_NETWORK_ACCESS_DENIED` к живому контрольному
endpoint. Это не проверка AppContainer, старого соединения или авторизованной сессии.

CA и WinINET proxy для этого Guest заданы временным частным тестовым helper;
автоматическая настройка нового Guest в установщик не добавлена. После остановки
Squid helper удалил собственный CurrentUser CA и proxy, затем Guest вышел штатно.
Shared PC удалил его учётную запись и профиль. Администратор из локальной GUI
консоли один раз запустил исходное фиксированное SYSTEM-задание Normal, без
сервера и загрузки кода. Свежий результат 0 подтвердил снятие обеих собственных
компонент; следующий обычный вход сохранил файлы, Java/Git и чтение USB, а готовая
Java-проба вновь подключилась напрямую по IPv4 и IPv6. Основной exam при этом
не запускался. Из-за ранее обнаруженного отсутствующего declared defaultuser0
Normal честно сохранил IdentityUnconfirmed/EffectiveMode=Unconfirmed при
SourceCleanupCompleted=true; конфигурация и ordinary roster не исправлялись.

До/после этого Normal совпали выбранные шесть полей 530 правил PersistentStore,
девять полей его профилей и хеши двух обычных файлов. До Normal, во время Guest
lifecycle, число правил изменилось с 601 до 530; причина не установлена, общее
равенство всех правил/фильтров за весь цикл не утверждается. Подробности и границы
проверки приведены в [отчёте 16 ноября](execution-2026-11-16.md).

На другой одноразовой VM отдельно проверен обычный Edge пользователя labstudent
(SID с окончанием 1001): PL/Moodle открывались по HTTPS при частном GPO canary,
посторонний адрес получил отказ proxy, прямой контрольный HTTP после включения
политики блокировался. Эта браузерная проба использовала временные пользовательские
CA/proxy настройки и не является поставкой автоматической настройки нового Guest.
Реальный NetworkService имел IsAppContainer=false; AppContainer остаётся pending.
Штатный Schannel curl имел отдельную ошибку проверки отзыва сертификата, поэтому
CONNECT 200 не подменяется утверждением о полном TLS-пути. Полный exam и
структурная файловая изоляция остаются заблокированы, FullReady=false.

Параметры GPO, `NotConfigured` и ограничение параллелизма описаны в
[официальной справке Set-NetFirewallProfile](https://learn.microsoft.com/en-us/powershell/module/netsecurity/set-netfirewallprofile).
