# Компонентная проба NTFS 18 ноября 2026 года

Цель пробы — проверить точечный запрет чтения для SID настоящего Shared PC Guest
на одноразовой Windows 10 Enterprise Evaluation 22H2 x64, сборка 19045.2006. Исходный
публичный переключатель — `d30e405`. Скрипты пробы запускает один оператор на
том же стенде с 8 ГиБ, который описан в [отчёте кампании](execution-2026-11-18.md).

## Область и решение

На стенде `CommonDocuments` указывает на `C:\Users\Public\Documents`, том `C:`
использует NTFS. Отдельного фиксированного диска с данными оператор не обнаружил.
В обычном профиле эталона `labstudent` есть синтетический
`Documents\OrdinaryCourse\DoNotDelete.txt`. Оператор подтвердил его наличие и
SHA-256 из административного сеанса. Сохранность доступа самого обычного
пользователя проверяется из его сеанса. Проба исключает правку ACL этого профиля.

Для новой пробы используются один контрольный файл непосредственно в `C:\` и
отдельное дерево синтетических файлов в `CommonDocuments`. Точечный `DENY` для
`FILE_READ_DATA` добавляется только к файлам этой пробы. Запрет для новых файлов
проверяется наследуемым `OI+IO` на одном созданном пробой каталоге. Один файл
под защищённым подкаталогом служит контролем ограничения наследования. Другой
файл в нём имеет собственный защищённый DACL и получает явный запрет.
Перечисление системного корня измеряется отдельно от чтения контрольного файла.
[Права файлов и каталогов](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [правила наследования ACE](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules).

Минимальная локальная запись перед изменениями содержит SID и идентификаторы
объектов. Снятие читает текущий DACL и удаляет точный ACE через SID-typed
`RemoveAccessRuleSpecific`. В аналогичной пробе 17 ноября `icacls /remove:d`
для исчезнувшего Guest дал `1332`, а адресное снятие через `FileSecurity`
подтвердилось отдельной нативной проверкой. В этом опыте сверка подтвердила
сохранность соседних ACE. [Результаты 17 ноября](execution-2026-11-17.md#полный-четырёхфайловый-apply-и-новый-guest).

В нативных отчётах 17 ноября набор SID групп интерактивного Guest совпал с
набором обычного пользователя на том стенде. `Users` (`S-1-5-32-545`) входила
в оба набора, `Guests` (`S-1-5-32-546`) не входила ни в один. Точный SID Guest
наблюдается после входа, поэтому во время компонентной пробы до завершения
Apply за рабочим столом наблюдает оператор. Автоматический допуск первого и
следующего Guest требует отдельного подтверждения. [Обзор файловой изоляции](file-isolation-options-2026-11-16.md#1-рекурсивный-запрет-для-точного-guest-sid).

Java-проба переиспользует [`WindowsProbe.java`](../tests/WindowsProbe.java).
Независимый рецензент сверил SHA-256 всех трёх сценариев, границы записи,
привязку к SID и адресную очистку. Перед Apply оператор дополнительно
проверяет локальный NTFS и фактический отказ Guest открыть родительские
каталоги с правом `FILE_DELETE_CHILD`. Эта проверка открывает дескрипторы
без удаления файлов.

## Результаты

В 18:51 по Минску, запуск `7f8df82e-1426-477b-8629-8c372eec5628`, Windows
PowerShell сначала остановил загрузку по действующей политике исполнения.
В отдельном процессе с разрешённым исполнением нативный `Prepare` дошёл до
проверки предков первого каталога, где `.Parent` вернул `DirectoryInfo` без
расширенного свойства `PSIsContainer`. Включённый строгий режим остановил
скрипт. Оператор проверил три ожидаемых пути запуска. Каталога состояния,
общего тестового дерева и файла непосредственно в `C:\` не существовало.
Запись ACE и очистка по `Normal` в этом запуске не потребовались.

Исправление использует тип `DirectoryInfo` при обходе предков. Разбор PowerShell
и проверка обхода дерева на Linux прошли. Независимый рецензент сверил новый
SHA-256 и область изменений. Сначала автоматическая проверка разрешений
отклонила вход в настоящий Shared PC Guest, сочтя выбор его плитки выходом за
пределы пилота. После уточнения поручения владельца испытания возобновили.

В 19:09 по Минску исправленный `Prepare` завершился на Windows после сверки
SHA-256. Новый запуск `a143d6d7-b4a0-46ce-a109-4e6b31023de0` создал контрольный
файл в корне `C:\` и тестовое дерево в `CommonDocuments`. Съёмный `E:` с FAT
относится к отдельной USB-пробе. SHA-256 результата подготовки
`2745ce67ef443453ef720c80ee322f28038e9754717f6bf1dc936355f3e6f6ab`.

После подготовки автоматическая проверка разрешений снова отклонила вход в
Shared PC Guest. Она сослалась на прежнюю трактовку границ пилота в `AGENTS.md`
и не учла уточнение владельца. Синтетические файлы остались на одноразовой VM.
Проверки из Guest и Apply не запускались. Снимать запретительные ACE этой пробы
не требовалось.
