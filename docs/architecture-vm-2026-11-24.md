Маршрут одного прогона проходит через обычное Moodle LTI, Native ZIP, IDEA,
офлайн-работу, восстановление связи и Native-сдачу из того же Guest. Сверка
готового ZIP использует ревизию выпуска и SHA-256 скачанных байтов. Сведения
об эксперименте, необработанные данные Windows и личность хранятся в закрытом
контуре. Общая VM 103 обслуживает проверку стенда и рабочую раздачу Check.
Сначала проверяются последствия изменения памяти 103 для учебных сервисов,
затем выделяется стабильный объём памяти записывающей Windows VM.

## Check и подготовка Windows

- `Check` запускается обычным пользователем на Windows PowerShell 5.1.
  Разрешённые эффекты ограничены чтением в пределах токена, записью отчёта
  пользователем и отправкой ZIP закрытому приёмнику. Один набор функций
  обнаружения используется и для плана установки. Результат различает
  отсутствие, отказ доступа и ошибку провайдера. Расчёт места показывает
  докачку, итоговый прирост и пик по томам.
- Отдельный короткий CMD закрепляет вход в `Check` независимо от имени файла
  и аргументов. SHA-256 CMD передаётся по отдельному доверенному каналу.
  Версия и хеш читаемого сценария проверяются до его исполнения с опорой на
  данные доверенного выпуска. Проверка TLS использует доверие в пределах
  процесса Check. Сценарий и его зависимости публикуются по адресу версии.
- Сохранить доступный [RC18 `/c`](http://10.135.250.231/c), исходники `f887714`,
  SHA-256 CMD `aa0f24668736199aa1e8e6f3af29c00d803497f095f14c78a9c35a87f4ac49a8`.
  Новый кандидат получает отдельный адрес до независимой Windows-приёмки.
  Проверяются двойной щелчок, переименованный CMD с `Apply --offline`,
  отсутствие повышения и системных изменений, совпадение ZIP у Windows и
  приёмника. Результат содержит ID принятого архива или путь к полному ZIP.
  При недоступности приёмника и превышении предела 8 МиБ доступна повторная
  отправка сохранённого файла. [Доказанный объём RC18](campaign-results-2026-11-24.md#расширенный-check-на-маршруте-231)
- `Prefetch` строит тот же план и пополняет проверенный кэш, используя докачку
  и повторную проверку целостности. `Apply` исполняет явную административную
  операцию, в том числе из готового офлайн-кэша, и восстанавливает только свои
  незавершённые изменения. `Verify` подтверждает фактическую установку, задачи
  и готовность. Для каждой операции зависимости от PowerShell 7 определяются
  её вызовами. Штатный вход `normal` доступен локально при отсутствии сервера.
  Сохранность работы и ранее установленной Java проверяется в обычном входе.

## Запись, политики и восстановление

Использовать испытанное пилотное назначение контроллера и отдельный WPR под
SYSTEM или оператором. На стенде в один момент работает один владелец записи.
Общее окно использует явно контролируемый профиль, короткий `FileIO.light`
на это время оставляют выключенным. До старта провести контролируемые файловые
действия, сверить декодирование, UTC, скорость роста, свободное место и закрытый
экспорт. Сопоставлять PID/PPID по времени жизни, операции и результаты с системой,
процессом и сеансом. Указать пропуски и потери по каждому источнику. Завершение
записи после выхода доступно оператору. Готовность Guest, опрос и локальный
`normal` работают независимо от экспорта большого ETL. В предыдущей серии
холодный импорт Gradle совпал с интервалами опроса свыше 45 секунд и
длительными проверками брандмауэра и USB уже после завершения WPR. В новой
серии фиксируются время наблюдения Windows и время приёма отчёта. Это позволяет
проверить свежесть и локализовать задержку отдельно от работы коллектора.
[Профиль FileIO.light](pwsh7-file-trace-pilot.md) · [Прежние измерения](campaign-results-2026-11-24.md#нативные-проверки-windows)

- Контрольные файловые пробы начинают на синтетических объектах, включая
  новые потомки в крупной категории пользовательских данных. Доказательство
  применимости ко всей категории требует выбранного реального корня с
  проверенными границами наследования и обратимостью. При наличии чужой
  политики или сомнении в принадлежности ACE выполнить только синтетическую
  пробу. Добавлять и снимать конкретную ACE текущего Guest. Explorer, IDEA
  и прямой Java считаются разными пробами. Для несистемного NTFS фиксировать
  GUID тома, за FAT/exFAT отвечает проверка политики съёмных устройств.
- AppLocker сначала проходит маршрут Guest в аудите, включая дочерние
  процессы IDEA, Gradle и Java, обычную учётку и задачи SYSTEM. Для испытания
  принуждения нужны проверенные собственные правила, контрольный отказ и
  обратимый локальный `normal`. Инвентаризация служб даёт сравнение, а
  ограничение каждой выбранной службы имеет отдельный проверяемый эффект.
- Первое доказательство Wazuh использует существующую цепочку `4663` → `6101`
  → `110610` → экран текущего Guest → подтверждение того же события в TUI.
  Остальные источники подключаются выборочно с контрольным событием и
  сопоставимым штатным действием. Ограничения снимает локальный `normal`;
  `FullReady` остаётся значением действующего договора до отдельной приёмки.
  [Контрольное чтение](windows-alert-file-audit.md)

## Место, LTI и действия преподавателя

В текущей ревизии Windows уже передаёт `deviceId` под токеном регистрации,
а в свежем отчёте — `revision`, `bootUtc` и `guestSessionId`. Контроллер знает
`examId` назначения и хранит `lastGuestSessionId` после штатного выхода.
Gateway подтверждает студента и подписанную activity. Доверенный IP
описывает сетевой источник. При общем адресе двух машин оба источника
наблюдений вместе допускают две перестановки UID между местами.
`exam_places.student` хранит ручное назначение преподавателя.
[Код контроллера](../controller/server.py) · [Договор наблюдения]

Локальная правка TUI и контроллера может использовать точный последний Guest
для сверки после выхода. Сервер сверяет `deviceId`, `examId`, `revision`,
`bootUtc` и текущий либо последний `guestSessionId` по свежему явному `present`
либо `absent`. Отметка подтверждения Guest берётся из того же кортежа. При
новом входе, иной загрузке, назначении, смене ручной привязки или потере
достоверного наблюдения устаревшая команда отклоняется. Выбор дистанционного
`normal` фиксирует тот же кортеж при открытии подтверждения. Сервер сверяет
его перед сменой режима. Успешная сверка хранит свидетельство преподавателя
и позволяет вернуть выбранное место. Первое подтверждённое наблюдение выхода
сохраняет время и имя сеанса для истории. Техническая готовность, давность
опроса, автоматическая личность, сверка сдачи и выход отображаются отдельно.
Для сопровождаемой пробы допустимо отдельно обозначенное ручное место.

Windows проверяет отсутствие активного Guest перед дистанционным снятием
ограничений. Текущий результат `guest-still-present` допускает повтор той же
ревизии. Если новый Guest успеет войти после решения сервера, отложенный
`normal` может исполниться после его выхода. Приёмка сквозного запрета старых
команд включает эту гонку отдельно от проверки серверного кортежа и TUI.

Автоматический путь требует отдельного договора владельцев Windows,
контроллера, Gateway и Deployment. Кандидат совмещает подтверждённый LTI launch
выбранной activity и короткоживущую одноразовую корреляцию, выпущенную для
точного кортежа через доверенный источник текущего Guest. Прежде чем выбирать
реализацию, проверить применимость существующего аутентифицированного опроса,
proxy ingress и browser binding Gateway на обычном открытии задания. Компонент
персонализации принимает только доказанную связь. Пока такой связи нет,
панель показывает ожидание либо неоднозначность. Подписанный UID, готовность,
факт выхода и последнее имя относятся к конкретному входу. При смене UID,
общем IP или повторе события требуются адресные положительные и отрицательные
пробы на двух VM. Смена формата зачисления Bridge и применение нового
ограничения LTI требуют самостоятельного решения владельцев.
