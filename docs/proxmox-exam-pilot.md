# Серверная VM экзаменационного пилота

Пилот, начатый 19 ноября 2026 года, использует отдельную VM для тестовой Moodle,
PrairieLearn, Gateway/Bridge, Nginx, Squid, контроллера и Wazuh. Deployment
задаёт контейнеры, данные и клиентские порты. Platform поставляет образы и
правила импорта курсов. exam-lab задаёт требования к экзаменационному режиму,
допуску Windows и восстановлению обычной работы.

## Размещение

| Параметр | Значение |
| --- | --- |
| Имя и VMID | `exam-lab-pilot`, `103` |
| Гипервизор | Proxmox VE 9.2.20 |
| Образ | Ubuntu Server 26.04 LTS amd64, `release-20260927` |
| SHA-256 образа | `8800651811af9a85465ad1d552add729947bb16488dddb4a9b5305a3d97332b2` |
| CPU и память | 12 vCPU, тип CPU `host`, 28 ГиБ RAM без ballooning с 21 ноября |
| Диск | 100 ГиБ на `local-lvm`, VirtIO SCSI Single с I/O thread и TRIM |
| Сеть | VirtIO на `vmbr0`, без тега VLAN, `10.135.250.231/16` |
| Загрузка | SeaBIOS, `scsi0`, последовательная консоль, автозапуск на узле выключен |

При первом запуске пилоту выделили 4 vCPU и 12 ГиБ RAM. В момент той
сверки у узла было 62,4 ГиБ RAM. Действующим VM и контейнерам без учёта
шаблонов было выделено 38 ГиБ, из них 24 ГиБ запущенным. При исходных
12 ГиБ пилота расчётный остаток составлял 12,4 ГиБ при одновременном
запуске всех существовавших гостей.
На `local-lvm` оставалось около 1,47 ТиБ, отдельное хранилище `local`
поддерживает резервные копии и имело около 467 ГиБ свободного места.
Шлюз отвечал. С моста гипервизора отправлено три запроса ARP к выделенному
адресу, ответов не получено. Перед повторным использованием адреса проверяют
актуальность выделения, прямой ARP и наличие чужого ресурса с тем же VMID.

Использован проверенный образ из кэша Platform. Его SHA-256 совпал с закреплённой
ревизией Platform и манифестом Canonical. Подпись манифеста проверена ключом
`UEC Image Automatic Signing Key` с отпечатком
`D2EB 4462 6FDD C30B 513D 5BB7 1A5D 6C4C 7DB8 7C81`.
[Выпуск образа](https://cloud-images.ubuntu.com/releases/resolute/release-20260927/) ·
[Проверка Canonical](https://ubuntu.com/docs/public-images/public-images-how-to/verify-image-checksum/)

## Повтор подготовки

1. Через предусмотренный QCL-NEGF доступ сверить VMID командой `pvesh get /cluster/nextid`,
   ресурсы узла, свободный объём хранилища, параметры моста и адрес. Запросить
   точные параметры шлюза, DNS и административного входа из защищённой локальной
   записи. Источники `10.0.0.0/8` описывают клиентов служб. Длина префикса VM равна 16.
2. Штатными `qm create`, `qm disk import`, `qm disk resize` и `qm set`
   создать отдельную VM с параметрами из таблицы. Установить `link_down=1`
   на `net0`, подключить собственный cloud-init диск и задать статический
   `ipconfig0`. Импортировать проверенный образ чтением. Защитить новую VM
   от удаления через `protection=1`.
3. Взять [пример cloud-init](../vm/proxmox/exam-lab-pilot-cloud-init.yaml.example).
   Заменить `REPLACE_WITH_OPERATOR_PUBLIC_KEY` выделенным публичным ключом
   и `192.0.2.10` фактическим IPv4 оператора из защищённой записи. Для
   отдельно разрешённого административного входа с узла Proxmox заменить
   `192.0.2.11` точным адресом источника, который видит VM. При единственном
   источнике удалить второй адрес из набора SSH. На VM 103 проверены адреса
   `10.135.0.184` для QCL-NEGF и `10.135.250.201` для узла Proxmox.
   Для прямого SSH из Muon на ноутбуке в `allow_pilot` добавлено отдельное
   правило `ip daddr 10.135.250.231 ip saddr 10.160.74.251/32 tcp dport 22 accept`.
   Для восстановления подставьте фактический адрес административного клиента
   и проверьте файл `nft --check --file /etc/nftables.conf` перед применением.
   Пример включает вход по ключу для выделенного администратора. Cloud-init
   включает штатный `nftables` с отказом для прочих входящих соединений.
   Правило до Docker DNAT на виртуальном интерфейсе защищает также
   публикуемые контейнерные порты. Глобальный firewall Proxmox остаётся
   в исходном состоянии.
4. Запустить VM со снятым сетевым линком. Дождаться в последовательной консоли
   подтверждения загрузки таблицы nftables и получить публичный ключ SSH-сервера.
   Подключить линк после повторной адресной проверки, закрепить полученный
   ключ и проверить адрес, маршрут, разрешённый административный вход
   и отказ с другого источника.
5. После передачи VM Deployment открывает только нужные порты для `10.0.0.0/8`.
   В этой VM сетевой интерфейс называется `eth0`. Перед открытием портов
   сверяют имя интерфейса в правиле `prerouting` с фактическим маршрутом VM.
   Проверять фактический источник после маршрутизации и отказ с другого
   испытательного сегмента. Вход в Proxy, Moodle, PrairieLearn, опрос контроллера
   и доставка Wazuh проверяются отдельно. Прямые входы к хранилищу, внутренним
   HTTP-службам и административным интерфейсам остаются закрыты.

## Первый запуск 19 ноября

VM загрузилась с отключённым линком. Cloud-init дошёл до конца после ожидания
сети и подтвердил активную таблицу nftables в последовательной консоли.
Публичный SSH-ключ закреплён из этой же консоли. После подключения линка
разрешённый SSH-вход прошёл со строгой проверкой ключа. Ubuntu сообщила версию
26.04.1 LTS, адрес `10.135.250.231/16` на `eth0`, активный маршрут через
согласованный шлюз и 94 ГиБ свободного места в корневой файловой системе.
Соединение SSH с другого источника в той же подсети отклонено по тайм-ауту.
Из VM получены ожидаемые ответы HTTPS от официальных источников Ubuntu, Docker,
Docker Hub, GitHub Container Registry и Wazuh. Имя интерфейса из начальной
настройки уточнили до публикации контейнерных портов и передали Deployment.

Для возобновления ранее настроенного стенда от имени его администратора
на VM 103 запустите [сценарий запуска](../scripts/vm/start-proxmox-pilot.sh).
Публикация установщика использует существующий HTTPS-вход контроллера.
Порядок подготовки файлов и подключения маршрутов приведён в
[инструкции приёмки](manual-proxmox-acceptance.md#подготовка-proxmox).

## Остановка и восстановление

Для запуска сохранённого окружения используйте
[сценарий запуска пилота](../scripts/vm/start-proxmox-pilot.sh) в окно без
активных сдач. Установленный контроллер с TUI поднимается штатной systemd-службой.
Для исторического пилота 21 ноября в закрытом каталоге
`$HOME/exam-lab-campaign/transfer/handoff-java` лежат два ZIP выбранной работы:
исходный `original.zip` и проверенная заготовка `canary.zip` с исправлением
кириллических аргументов. Воспроизведение этой исторической подмены требует
явного `EXAMLAB_REPUBLISH_LEGACY_STARTER=1`. При штатном запуске fixture
использует заготовку из закреплённого Native.
[Исправление заготовки](https://github.com/BSU-RFCT-Afonenko-Courses/Java/pull/45)

Перед остановкой сверить из Windows и на сервере подтверждение последней сдачи.
Остановить запись тестовых сервисов, сохранить конфигурацию, регистрации
и данные. Штатно выключить только VM пилота через гостевую ОС или
`qm shutdown 103`, затем проверить `qm status 103`.

Копию холодной VM создают штатным `vzdump` на `local`, вне её диска
`local-lvm`. Доступ к копии ограничивают, поскольку она содержит ключи
и тестовые данные. Пробная VM для восстановления получает свободный VMID
и поднимается с отключённым линком, пока не проверены адрес и границы
изоляции. Критерий восстановления — фактическое чтение тестовой сдачи
и регистраций. До такой пробы считать восстановление непроверенным.
