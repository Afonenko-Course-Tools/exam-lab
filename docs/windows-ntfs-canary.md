# Файловая проба сопровождения Shared PC Guest

Назначение пробы — на одноразовой Windows VM проверить, блокируют ли штатные
NTFS ACE чтение существующих и новых контрольных файлов и можно ли адресно
восстановить исходные права. Для каждого входа оператор выбирает плитку Guest
сам, до передачи управления студенту. У основного `exam` остаётся
`FullReady=false`.

## Доступ до входа

Shared PC создаёт отдельную локальную учётку при каждом выборе Guest. В пробе
17 ноября использовавшиеся группы ordinary и Guest совпали, SID встроенной
группы Guests (`S-1-5-32-546`) в их токенах отсутствовал. `AtLogOn` запускается
после появления учётки и сам по себе не задерживает доступ. Документированный
SharedPC CSP не предоставляет отдельный постоянный SID или барьер, который
ожидает применения ACE к этому новому SID. [Shared PC и создание Guest](https://learn.microsoft.com/en-us/windows/configuration/shared-pc/shared-devices-concepts#account-models),
[SharedPC CSP](https://learn.microsoft.com/en-us/windows/client-management/mdm/sharedpc-csp),
[наблюдения 17 ноября](execution-2026-11-17.md#полный-четырёхфайловый-apply-и-новый-guest).

Групповая политика `Run logon scripts synchronously` задерживает запуск
Explorer до завершения сценария входа. Сам сценарий получает права вошедшего
пользователя. Для обновления административных ACL потребовалась бы отдельная
повышенная задача и доказательство, что система удерживает доступ при отказе
этой задачи. Задержку Explorer поэтому учитываем как наблюдаемую возможность
оболочки. [Синхронный запуск в ADMX](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-scripts#run_logon_script_sync_2),
[права сценария входа](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/dn789196(v=ws.11)).

`RestrictLocalStorage` задаётся при подготовке Shared PC. В отдельной нативной
пробе он ограничил навигацию и диалог IDEA, а чтение известного пути из Java
сохранилось. Conditional ACE проверяет членство по токену. Кандидат с
группой-исключением требует заранее включить каждую обычную учётку, отдельно
проверить административные и служебные токены и обеспечить доступ к новому
профилю Guest. В ходе этой пробы членство и политика учёток сохраняются.
[Проба RestrictLocalStorage](execution-2026-11-16.md#shared-pc-restrictlocalstorage-включение-кандидата),
[условные ACE](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-definition-language-for-conditional-aces-),
[оценка кандидата](file-isolation-options-2026-11-16.md#2-conditional-ace-ordinary-исключён-без-привязки-к-guest-sid).

Найденный локальный путь сопровождается преподавателем на консоли. Оператор
удерживает управление от выбора плитки до подтверждения ограничений в том же
сеансе. Любой выход, смена SID или сеанса, преждевременная передача ввода либо
ошибка проверки прекращает допуск. Подготовка файлов предшествует переходу к
Moodle → Gateway → PrairieLearn → IDEA → сдача. Учётный UID, назначение работы и
подтверждение сдачи проверяются отдельно в договоре учебных сервисов. Windows
владеет локальными путями, SID и адресным снятием ACL. Deployment и Platform
сохраняют свои конфигурации и учебные данные. Для файловой пробы достаточно
штатных локальных API и уже существующей Java-пробы.

## Контрольные данные и права

Используйте Windows PowerShell 5.1 x64 в одноразовой VM. Независимый рецензент
сверяет файлы и SHA-256 перед запуском. Оператор создаёт новый GUID прогона и
выбирает существующий обычный профиль, из которого выполнен выход, например
`labstudent` на эталоне. У этого пользователя отдельно сверяются учебные файлы и
работа IDEA до/после. В `-DataRoot` допускается корень **нового выделенного
виртуального** диска NTFS, подготовленного оператором. Если отдельного диска нет,
сценарий запускают без этого параметра и строку приёмки тома отмечают `NOT_TESTED`.

Свежие контрольные пути с GUID создаются непосредственно в корне Windows, в
обычном профиле, непосредственно в `%PUBLIC%`, под `ProgramData` и на указанном
томе. Существующие
тестовые файлы получают изначально защищённый DACL с чтением для `Users`.
Это синтетический маркер в чужом профиле. Для реального учебного файла из этого
профиля отдельно измеряется штатный доступ Guest без правки ACL файла. Оператор
фиксирует чтение настоящего учебного файла обычным пользователем. Ожидаемый отказ
Guest сам по себе не свидетельствует о действии добавленного правила.

Первая проба 19 ноября размещала общий маркер в `C:\Users\Public\Documents`.
Исходное чтение прошло для всех пяти маркеров, но настоящий Guest открыл
`Public\Documents` с `FILE_DELETE_CHILD` и `DELETE`, а каталог самого маркера —
с `DELETE`. Оператор остановил этот прогон до Apply. Для продолжения используется
новый GUID и маркер непосредственно в `%PUBLIC%`, где в исходной пробе эти права
получить не удалось. Права `Public\Documents` сохранились. Этот отдельный
отрицательный результат учитывается при оценке широкого покрытия общих данных.
[Право удаления на объекте и родителе](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilea#remarks).

На уже созданный маркер сценарий ставит точный явный `DENY FILE_READ_DATA` для
текущего SID. Родительские правила `OI+IO` ограничивают чтение вновь созданных
наследующих файлов внутри новых каталогов пробы. Корень Windows проверяется
отдельным файлом: наследуемого правила на корне тома или на родителе за пределами
каталога пробы нет. Явный allow на дочернем объекте проверяется раньше
унаследованного deny. Защищённый DACL, перемещение файла в пределах тома, уже
открытый дескриптор и существующие объекты вне пробы требуют своей оценки.
[Права чтения и создание файла](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights),
[наследование](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules),
[порядок проверки ACE](https://learn.microsoft.com/en-us/windows/win32/secauthz/order-of-aces-in-a-dacl).

Сценарий проверяет локальный NTFS, предков без reparse points, идентификаторы
объектов и единственную жёсткую ссылку каждого существующего файла. Выполняйте
действия последовательно. До `Apply` проверяются неизменность контрольных ACL
и отсутствие ACE текущего SID. Перед первым изменением в закрытом каталоге
состояния фиксируется SID. `Normal` читает текущие ACL и снимает только точные
записи этого SID, сначала наследуемые правила каталогов. Исходные SDDL и хеши
используются для сверки. Если файл был заменён, ACE отличается или исходная ACL
не совпала, состояние сохраняется для разбора. Успех локального `Normal`
подтверждается штатными чтениями, в том числе при удалённой после выхода учётке
Guest, и отдельной проверкой USB и сети по их инструкции.

## Порядок прогона

Разместите два сценария из `tests` и `WindowsProbe.class` в защищённом от записи
обычного пользователя каталоге, доступном ему на чтение. Для компиляции
используйте установленный JDK, например `javac -d <каталог> WindowsProbe.java`.
Подготовьте обычный проект с контрольным SHA-256 и включите сетевой/USB-компоненты
по их собственным инструкциям до выбора Guest, если цель включает общий цикл.

1. В административном терминале выполните подготовку. Пример предполагает,
   что опциональный новый том уже получил букву `T:`.

   ```powershell
   $run = [guid]::NewGuid()
   $canary = 'C:\Program Files\ExamLab\NtfsCanary\ntfs-canary.ps1'
   & $canary -Action Prepare -RunId $run -OrdinaryName labstudent -DataRoot T:\
   ```

   Сохраните результат `Prepared` и время, набор путей `Existing` и `Future`.
   Оператор сверяет список локальных учёток до выбора плитки после штатного
   выхода ordinary. Из ordinary до пробы запишите SID терминала, группы,
   SHA-256 учебного файла и результат открытия проекта.

2. С консоли выберите штатную плитку Guest. Запишите время выбора, появления
   рабочего стола и оглашения SID. В Windows PowerShell этого сеанса создайте
   `$existing` из всех значений `Detail.Existing` результата `Prepared` и вызовите
   пользовательский сценарий. `$java` — полный путь к установленному `java.exe`,
   `$classes` — защищённый каталог с `WindowsProbe.class`, `$sid` — SID,
   подтверждённый `whoami /user` в этом же окне.

   ```powershell
   $reader = 'C:\Program Files\ExamLab\NtfsCanary\ntfs-canary-read.ps1'
   & $reader -Expected read -Paths $existing -JavaPath $java -ProbeClassPath $classes -ExpectedSid $sid -CheckMutationRights
   ```

   Сохраните `Pass` для каждого файла, группы токена и Session. Получение кода 5
   при открытии с правом на замену проверяет, что Guest не сможет менять маркеры
   и известную цепочку каталогов. Проверка граничных прав не удаляет объекты.
   При любой ошибке остановите пробу до применения. Закройте окна, которые могли
   заранее открыть контрольные файлы. Во время прогона работает один оператор.

3. В первой итерации из административного терминала запустите `Apply` с
   `-StopAfterFirst`. Ожидается ошибка после записи одного ACE. Требуемый
   статус допуска в этом состоянии — закрыт. В Guest прочитайте отдельно
   первый маркер `SystemRoot` с ожидаемым `deny`, прочие с ожидаемым `read`.
   Затем снимите изменение локально и повторите `Normal`. В том же Guest
   снова ожидайте `read` у всех исходных маркеров.

   ```powershell
   & $canary -Action Apply -RunId $run -GuestSid $sid -OperatorConfirmedGuest -StopAfterFirst
   & $canary -Action Normal -RunId $run
   & $canary -Action Normal -RunId $run
   ```

4. Выполните полный `Apply` и создайте новые наследующие маркеры. В том же
   Guest повторите пользовательский вызов с `-Expected deny` для `Existing`
   и для всех `Future`. В проводнике проверьте навигацию к каждому контрольному
   каталогу и копирование маркера в собственный профиль. В диалоге IDEA
   введите его точный путь и попробуйте открыть. Фиксируйте исход копирования
   и чтения; если появилось предложение повысить права, отмените его. В
   собственном чистом профиле сохраните проект, запустите его и откройте
   после закрытия IDEA. По необходимости отдельно проверяйте Debug и Git.

   ```powershell
   & $canary -Action Apply -RunId $run -GuestSid $sid -OperatorConfirmedGuest
   & $canary -Action NewFiles -RunId $run
   ```

   Для данного запуска передавать управление студенту можно только в пределах
   согласованной одноразовой VM с синтетическими данными, после проверок
   файлов, USB и сети из этого сеанса и подтверждения преподавателя. При
   неизвестном охвате обычных данных место закрыто. Условие обычного
   защищённого экзаменационного запуска требует независимой приёмки.

5. После сдачи или завершения пробы выйдите из Guest штатно. Убедитесь, что
   прежний Guest отсутствует в локальных учётках, `Win32_UserProfile` и его
   каталоге. Отключите соединение с контроллером/прокси для автономной проверки.
   На самой VM из той же административной учётки, что выполняла `Prepare`,
   запустите NTFS `Normal` и повтор, затем при общем цикле штатный `normal` USB/сети. Из обычного сеанса сверяйте
   чтение исходных и новых маркеров, исходный учебный файл, Git, IDEA и
   виртуальный USB. Прямые соединения повторите после возврата связи.

6. Начните отдельный GUID-прогон с новым `Prepare`. До нового Apply проверьте
   чтение прежних маркеров. Сверьте, что SID и чистый профиль отличаются от
   первого Guest. Для второго полного прогона повторите действия 2, 4 и 5.
   Укажите время применения для каждого SID и время до сопровождаемого допуска.
   Не меняйте старые диски или тома. Если `Normal` не завершился, второй допуск
   закрыт до устранения причины. Удаление синтетических путей из сохранённой
   VM — после приёмки наблюдений и сверки точного GUID; сценарий сохраняет их
   для измерений и ничего не удаляет из данных ordinary.

## Что фиксировать

Запишите сборку Windows, объём RAM, ревизию и хеши, количество объектов по
категориям, `ElapsedMs` каждого действия, SID без публикации целиком и
UTC-время контрольных точек. Для каждого состоявшегося чтения запишите интерфейс
(Explorer, IDEA, .NET, Java), ожидаемое и фактическое поведение. Отдельно
запишите момент первого опроса, окончание машинных политик, выбор плитки, появление
рабочего стола, завершение Apply, последнюю успешную проверку и подтверждение
преподавателя. `Applied` сообщает о проверке ACE. Допуск требует нативной
проверки действия правил в том же Guest.

Для выпуска широкого файлового механизма требуется измерить полный проход по
подготовленному дереву данных, исключения системных и программных каталогов и
чистого профиля, доступ с иных фиксированных томов, ProgramData и чёткую границу
для будущих файлов. Надо проверять примеры с явными и защищёнными DACL и
неуникальными путями; оценить нагрузку на аудиторной конфигурации 8 ГБ и
восстановление обычных занятий. Продолжительность на десятке синтетических
объектов полезна для стенда и не измеряет время полного прохода. Автоматический
допуск и результаты массовой политики отражаются отдельно от этой пробы.

Для следующей пробы сначала составьте реестр областей по фактическим системным
путям Windows. На системном томе отделите действующие Windows, Program Files,
Program Files (x86) и рабочий профиль этого Guest. В область данных входят
файлы непосредственно в корне, чужие профили, общие данные и прочие доступные
каталоги. Для ProgramData отдельно определите машинные каталоги, чтение которых
необходимо установленным учебным инструментам. На остальных фиксированных
томах учтите весь доступный набор данных. `Get-CimInstance Win32_UserProfile`,
системные известные каталоги и сведения о локальных томах дают исходные границы;
названия интерфейса и путь профиля предыдущего Guest для этого непригодны.
Сравните инвентаризацию с доступом из реального Guest и отметьте каждый пропуск,
особенно точки повторного анализа, жёсткие ссылки между областями, отдельные
точки подключения и тома без NTFS. Результат инвентаризации нужен до изменения
первой ACL.

Оцените отдельными проходами число файлов и длительность обхода, проверку ACL,
запись и снятие ACE. Сверяйте целостность проекта обычного пользователя и
сохранность соседних правил. Для тех данных, куда во время экзамена допустима
запись с обычной учётки, отдельно измерьте создание с обычным наследованием,
явный allow, protected DACL и перемещение в пределах тома. Явный запрет
существующих файлов, наследование и адресное снятие должны опираться на
объекты той же области. Для точного SID понадобятся отдельные проходы первого
и следующего Guest; сравнивать их время полезно только при одинаковом объёме
данных и одинаковом состоянии Windows.
